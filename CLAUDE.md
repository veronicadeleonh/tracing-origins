## Commands

python src/build_dataset.py          # layer 1 Met    -> data/processed/met_objects.csv
python src/build_dataset_louvre.py   # layer 1 Louvre -> data/processed/louvre_objects.csv
python src/build_dataset_bm.py       # layer 1 BM     -> data/processed/bm_objects.csv

python src/build_geography.py          # layer 2 Met    -> data/processed/geography.csv
python src/build_geography_louvre.py   # layer 2 Louvre -> data/processed/geography_louvre.csv
python src/build_geography_bm.py       # layer 2 BM     -> data/processed/geography_bm.csv

python src/export_web_data.py        # junta layer 1+2+3 de TODOS los museos -> web/src/data/objects.json
python src/make_map.py               # opcional: mapa estático Folium -> maps/map_pilot.html (fallback, no es la experiencia principal)

# App web (la experiencia principal)
cd web
npm run dev      # servidor local con hot reload — requiere objects.json ya generado
npm run build    # tsc -b && vite build -> web/dist

# Tests (pipeline de Python)
pytest                # corre tests/ -- ver alcance abajo
pytest -v tests/test_geocode.py  # un solo archivo, verbose

`export_web_data.py` no se corre solo — cada vez que cambia algo en `data/processed/` o `data/enrichment/` hay que volver a correrlo antes de ver el cambio en la app. El frontend (`web/`) tiene linter (`npm run lint` → `oxlint`, configurado en `web/.oxlintrc.json`) pero no tiene test suite.

**Test suite del pipeline de Python (19/08)**: cobertura deliberadamente acotada, no exhaustiva — `tests/test_geocode.py` + `tests/test_museum_id.py` (22 tests), enfocados en `geocode.py` porque es la parte del pipeline con mayor historial real de bugs (ver el bug de matching por substring del 17/08, arriba). `tests/conftest.py` agrega `src/` a `sys.path` porque `src/` es una colección de scripts, no un paquete instalable — no hay `setup.py`/`pyproject.toml` ni se planea agregar uno solo para esto. Los tests de `resolve_origin_louvre()` reproducen los dos casos reales del bug del 17/08 (Dendéra/"sur" y Luristán/"Ur" — este último es el que efectivamente detecta una reintroducción del bug, ver comentario en el test; el de Dendéra pasa igual con el matcher viejo porque "Dendéra" está antes que "Ur" en la lista, así que queda como test de correctitud del caso documentado, no de regresión). No hay tests para `fetch_*.py`/`build_dataset*.py`/`build_geography*.py` (requieren red o fixtures de datos crudos grandes) ni para el frontend — queda anotado como próxima ronda si hace falta, no bloqueante.

## Arquitectura

### Modelo de datos — 3 capas, nunca mezcladas

1. **Layer 1** (`build_dataset*.py` → `data/processed/<museo>_objects.csv`): metadata tal cual la da cada museo. No se calcula ni interpreta nada acá.
2. **Layer 2** (`build_geography*.py` → `data/processed/geography_<museo>.csv`): punto de origen geográfico, inferido por nosotros vía `geocode.py`. Separado de layer 1 a propósito: es una inferencia nuestra, no un dato del museo.
3. **Layer 3** (`data/enrichment/context.csv` + `provenance_events.csv`, poblado a mano, sin script de descarga): investigación histórica del recorrido de la pieza. **No clasifica piezas como "robadas"/"no robadas"** — el objetivo es documentar el recorrido (creación → excavación/hallazgo → transferencias → adquisición del museo → hoy), no emitir un veredicto. `event_type` es un vocabulario controlado no acusatorio (`creation`, `excavation`, `transfer`, `sale`, `gift`, `bequest`, `exchange`, `acquisition`, `loan`, `restitution`, `other`). La gran mayoría de las piezas no tiene fila en layer 3 todavía — es el estado por defecto, no una excepción, y `export_web_data.py`/`make_map.py` lo tratan como opcional.

`export_web_data.py` es el único punto que junta las 3 capas (por `objectID`) y las tira a `web/src/data/objects.json`, que consume la app React. No depende de `folium` a propósito — es solo transporte de datos.

### Multi-museo: un builder por museo, mismo shape de salida

Cada museo tiene su propio `fetch_*.py` / `build_dataset_*.py` / `build_geography_*.py` porque el shape de datos de origen es distinto en cada API/sitio, pero los tres devuelven CSVs con las mismas columnas (`objectID`, `sourceMuseum`, `sourceObjectID`, `title`, etc. en layer 1; `origin_label/precision/lat/lon`, `museum_lat/lon` en layer 2). `export_web_data.py` los itera vía `MUSEUM_SOURCES` (lista de pares objects/geography csv) — agregar un museo nuevo es agregar su par de builders + una entrada en esa lista, sin tocar el resto.

`objectID` está namespaceado como `"<museo>:<id-nativo>"` (`met:96404`, `louvre:cl010277627`, `bm:Y_EA24`) porque el id crudo no es único entre museos — ver `src/museum_id.py`. Esto NUNCA se aplica a `data/raw/*.json` (el snapshot crudo se congela tal cual lo entrega cada fuente); se aplica recién al construir layer 1.

### Geocodificación (`geocode.py`)

Sin llamadas a Nominatim en bulk (prohibido por su política de uso) — es una tabla de coordenadas armada a mano, con un `resolve_origin_*()` por museo porque cada fuente da la geografía en un formato distinto:

- **Met** (`resolve_origin`): `country`/`region`/`subregion` estructurado, con fallback a texto libre de `culture` para los departamentos Asian Art y Greek/Roman Art (casi nunca completan country/region/subregion — ahí el único dato confiable es `culture`, ej. "Roman, Cypriot"; el fallback matchea por keyword, más específico primero, para que eso resuelva a Chipre y no a Italia).
- **Louvre** (`resolve_origin_louvre`): texto libre en francés, prioridad `placeOfDiscovery` > `placeOfCreation` > `provenance`, formato jerárquico "Sitio (Región->País)".
- **BM** (`resolve_origin_bm`): texto libre en inglés con prefijo de etiqueta ("Excavated/Findspot:", "Found/Acquired:", "Made in:"), prioridad `findspot` > `productionPlace`.

Cada build script imprime las etiquetas sin resolver al correr — expandir las listas de keywords (`*_SITE_COORDS`/`*_COUNTRY_KEYWORDS`) cuando se repiten es el mecanismo esperado de mejora incremental, no un bug a corregir de una.

**Label mostrado vs. texto matcheado (17/08)**: las listas `*_SITE_COORDS`/`*_COUNTRY_KEYWORDS` matchean contra el texto crudo tal cual viene de cada fuente (inglés para Met/BM, francés para Louvre) — esa palabra clave nunca se traduce, tiene que seguir encontrando el dato crudo. Lo que sí se traduce es el `origin_label` final que ve el usuario en la ficha de la pieza (`ObjectDetail.tsx`, "Hecho en {originLabel}"): las tres `resolve_origin_*()` pasan el nombre ya resuelto (sitio/país/región matcheado, no el texto crudo completo) por `es_label()`, que busca un exónimo en el diccionario `ES_NAMES` y si no lo encuentra devuelve el nombre tal cual. Antes de este cambio, BM mostraba literalmente el findspot/productionPlace scrapeado con su prefijo ("Excavated/Findspot:", "Found/Acquired:", "Made in:") y a veces notas de registro larguísimas pegadas — ilegible para el visitante; Louvre mostraba el texto libre francés crudo en vez del sitio matcheado. `ES_NAMES` no pretende ser exhaustivo — cubre países y los sitios con exónimo español establecido y conocido; sitios arqueológicos sin traducción evidente se muestran tal cual (son nombres propios, no cambian mucho entre idiomas). Ampliarlo es el mismo mecanismo incremental que las listas de coordenadas: se agrega cuando se nota un nombre feo/sin traducir, no hace falta traducir todo de una.

**`originLabel` en inglés (17/08, segunda vuelta del toggle ES/EN)**: `resolve_origin()`/`resolve_origin_louvre()` devuelven ahora también `label_en`, resuelto vía `en_label()`/`EN_NAMES` (mismo mecanismo que `es_label()`/`ES_NAMES`, mismas claves — el Met casi no necesita entradas porque sus claves crudas ya son inglés correcto; el Louvre sí, porque sus claves son francés). El **BM es un caso aparte**: sus `display` en `BM_SITE_COORDS`/`BM_COUNTRY_KEYWORDS` nunca fueron una clave de diccionario reutilizable — eran texto final ad-hoc (a veces inglés crudo, a veces ya traducido a mano al español en rondas de curación anteriores), así que meterlos en `ES_NAMES`/`EN_NAMES` hubiera requerido las mismas ~90 entradas ad-hoc que ya vivían en la tabla. Se optó por restructurar ambas listas a **4-tuplas** `(keyword, display_es, display_en, coords)` con los dos idiomas explícitos en la fuente, sin capa de diccionario intermedia — `resolve_origin_bm()` ya no llama a `es_label()` en absoluto. `build_geography*.py` escribe `origin_label_en` (además de `origin_label`) en las 3 `geography_*.csv`; `export_web_data.py` lo expone como `originLabelEn`; `ObjectDetail.tsx`/`geo.ts` eligen el campo según `lang`, con fallback a `originLabel` si falta el par en inglés (no debería pasar — `origin.get("label_en") or origin["label"]` en cada build script es la red de seguridad).

**Bug de matching por substring plano, encontrado y corregido el 17/08**: las cinco listas de keywords (`CULTURE_KEYWORDS` del Met, `LOUVRE_SITE_COORDS`/`LOUVRE_COUNTRY_KEYWORDS`, `BM_SITE_COORDS`/`BM_COUNTRY_KEYWORDS`) matcheaban con `if keyword.lower() in texto.lower()` — substring plano, sin límites de palabra. Encontrado al investigar el Zodiaque de Dendéra (`louvre:cl010028871`) para layer 3: su `placeOfDiscovery` menciona "Chapelle Est d'Osiris **sur** le toit" (francés, "sobre"), y la keyword "Ur" (ciudad mesopotámica, en `LOUVRE_SITE_COORDS`) matcheaba como substring dentro de "sur" — la pieza se geocodificaba en Irak en vez de Egipto, sin que nada lo señalara (`origin_precision` decía "site", como si fuera un match legítimo). El mismo mecanismo de bug afectaba a **12 piezas del Louvre en total**, todas con coordenadas silenciosamente equivocadas antes de este fix: 7 piezas de Luristán + 1 de Asiria (matcheaban "Ur" dentro de "Luristan"/"Assyrie"), 1 de Asur ("Ur" dentro de "Assur"), 1 de Baalbek ("Ur" dentro de "plusieurs"), 1 de Atenas/Cápua ("Mari" dentro de "Maria"), y el propio caso de Dendera. Ninguna de las 12 tenía relación real con Ur o Mari (Siria) — se verificó el texto crudo de cada una antes de asumirlo. Fix: nueva función `_keyword_matches()` con `\b` (límites de palabra) vía regex, reemplazando los 5 sitios de matching por substring plano; además se agregaron las keywords que faltaban y que el bug había estado enmascarando (Dendera/Denderah, Asur, Baalbeck, Athènes, Luristan, Assyrie) a `LOUVRE_SITE_COORDS`/`LOUVRE_COUNTRY_KEYWORDS`, con sus entradas correspondientes en `ES_NAMES`/`EN_NAMES`. Verificado sin regresiones: Met sigue en 161/168 (96%), BM en 90/90 (100%), Louvre pasó de "215/239 resueltas, 12 de ellas mal" a 215/239 resueltas correctamente (mismo conteo total, coordenadas corregidas). Este bug es un recordatorio de que el mecanismo incremental de "agregar keywords cuando se repiten" (arriba) asume que el matching en sí es correcto — vale la pena revisar el matching, no solo la cobertura de la lista, si una pieza nueva investigada a fondo aparece en un lugar que no tiene sentido con su historia documentada.

**País moderno de origen / búsqueda "al revés" por país (19/08)**: nuevo campo `origin_country`/`origin_country_en`, separado de `origin_label` — `origin_label` sigue siendo lo más específico posible (un sitio arqueológico, una región histórica, un país), pensado para la ficha de la pieza; `origin_country` es siempre un país moderno reconocible (o `null` en el puñado de casos donde el origen es demasiado difuso para asignarle uno, ver abajo), pensado para filtrar/buscar. Dos mecanismos en `geocode.py`, según qué matcheó cada `resolve_origin_*()`:

- `KEYWORD_COUNTRY` — cuando lo que matcheó ya es (o corresponde 1:1 a) un país: las claves de `COUNTRY_COORDS`/`CULTURE_KEYWORDS` (Met) y `LOUVRE_COUNTRY_KEYWORDS` (Louvre), más `BM_COUNTRY_FIELD_OVERRIDES` para el BM (sus `BM_COUNTRY_KEYWORDS` ya traen `display_es`/`display_en` reutilizables directamente como país, salvo un puñado de excepciones: "Easter Island"→Chile, "Tibet"→China, "Trinidad"→Trinidad y Tobago, "New Guinea"→Papúa Nueva Guinea). Un puñado de regiones históricas sin país en el nombre se mapean a su país moderno más asociado sin ambigüedad real para este propósito (Luristán/Perse/Elam→Irán, Assyrie/Mésopotamie/Babylonie/Sumer→Irak, Anatolie→Turquía, Levant→Siria como aproximación). `"Proche-Orient"` (Louvre) y `"Middle East"` (Met) quedan **sin país a propósito**: son regiones demasiado difusas (todo el Cercano Oriente) para asignarles un solo país sin que sea engañoso — de ahí que 3 de las 469 piezas (2 Met, 1 Louvre) no tengan `origin_country`.
- `SITE_COUNTRY_BY_POINT` — cuando lo que matcheó es un sitio puntual (`LOUVRE_SITE_COORDS`/`BM_SITE_COORDS`/`SUBREGION_COORDS`/`REGION_COORDS`, ~150 puntos): no tiene sentido mantener un país a mano por cada sitio arqueológico, así que se generó **una sola vez, offline**, con el paquete `reverse_geocode` (dataset de ~10mil ciudades, sin red — mismo espíritu que "sin llamadas a Nominatim en bulk") corrido contra los puntos lat/lon que ya vivían en este archivo, y el resultado se horneó como tabla estática en el código fuente. `reverse_geocode` **no es una dependencia del pipeline en tiempo de ejecución** (no está en `requirements.txt`) — se instaló y usó una sola vez en una sesión de Cowork para generar estos ~150 pares, después se revisaron a mano. Un error real encontrado en esa revisión: Haida Gwaii (Columbia Británica, Canadá) resolvía a Estados Unidos porque la ciudad más cercana en el dataset de la librería era Metlakatla, Alaska — corregido a mano en la tabla.

Propagación por el pipeline: `resolve_origin()`/`resolve_origin_louvre()`/`resolve_origin_bm()`/`resolve_from_culture()` devuelven `country`/`country_en` junto con `label`/`label_en`/`precision`/`lat`/`lon`; `EDITORIAL_ORIGIN_OVERRIDES` (ver más abajo) también los trae cargados a mano (`met:910742`→Irak, `louvre:cl010256592`→Ucrania). `build_geography*.py` escribe `origin_country`/`origin_country_en` en las 3 `geography_*.csv`; `export_web_data.py` los expone como `originCountry`/`originCountryEn`. Resultado: 466 de 469 piezas con país (79 países distintos), los otros 3 son los casos "Middle East"/"Proche-Orient" de arriba.

Frontend (`geo.ts`/`App.tsx`): `groupByCountry()` agrupa **todos** los objetos (no solo los `visibleObjects` filtrados por museum-toggles/research-filter, a propósito — la idea es "¿qué piezas de este país hay en cualquiera de los 3 museos?", independiente de qué esté prendido en el mapa en ese momento). La UI es un input de texto + dropdown de sugerencias (nueva fila `country-search-row` en `top-controls`, debajo del filtro de investigación) — al elegir un país, se arma un pseudo-cluster (`{lat: 0, lon: 0, label, objects}`, mismo shape que `OriginCluster`) y se reusa `ClusterPanel`/`ObjectDetail` tal cual, sin componentes nuevos ni un tercer estado de panel: `PanelState` gana un campo opcional `kind?: "country"` que viaja junto con `cluster`/`object` (incluído en el `onBack`/prev-next existentes) para que `ClusterPanel` sepa mostrar una segunda línea por fila con el sitio de origen puntual y el museo (`showOriginAndMuseum`/`museums` props nuevas, opcionales — sin ellas el componente se comporta exactamente igual que antes, para el flujo normal de click en un punto del mapa) en vez de cultura/período/fecha, que no aportan tanto cuando los resultados vienen de sitios y museos distintos.

### Descubrimiento de objetos por museo — tres estrategias distintas

- **Met**: API pública con `departmentIds`, sin restricciones — `fetch_met.py --department <id>`.
- **Louvre**: la API JSON por objeto es real (`collections.louvre.fr/en/ark:/53355/cl<id>.json`), pero el sitio **bloquea `/search/export`** en `robots.txt` y la búsqueda interactiva tiene **CAPTCHA** — no hay forma automatizada de listar objetos por departamento desde el sitio mismo. Solución: Wikidata tiene `P9394` ("Louvre Museum ARK ID", ~480k registros) cruzable con `P195` (colección = departamento curatorial, como entidad Wikidata) vía SPARQL público. Se piden ordenados por `wikibase:sitelinks` descendente para priorizar piezas documentadas/conocidas ("piezas bandera"). QIDs de departamento usados: Antigüedades Egipcias `Q3044749`, Antigüedades Orientales `Q3044751`, Antigüedades Griegas/Etruscas/Romanas `Q3044747`, Arte Islámico `Q3044748`.
- **BM**: no tiene API pública, y el puente equivalente por Wikidata (`P8565`, "British Museum object ID") **no funciona bien** — casi ningún objeto tiene el departamento curatorial cargado en `P195`, y varios valores de `P8565` no traen el prefijo de letra que la URL real necesita (tiran 404 tal cual). Se raspa directo `/collection/object/<id>` (permitido por robots.txt, que solo bloquea `/search*`, `/admin/`, etc.), pero el robots.txt pide **`Crawl-delay: 20`** (20 segundos entre requests) — se respeta a rajatabla en `fetch_bm.py`, así que bajar piezas ahí es lento. Sin descubrimiento automatizado confiable, `SEED_OBJECT_IDS` en `fetch_bm.py` es una lista curada a mano, anclada en la página oficial de ["contested objects"](https://www.britishmuseum.org/about-us/british-museum-story/contested-objects-collection) del propio Museo (Benin Bronzes, Asante Gold Regalia, Maqdala, Moai, Parthenon Sculptures) — ampliarla es manual, no hay atajo.
  - **WAF por User-Agent**: `britishmuseum.org` devuelve 403 ante cualquier User-Agent que no matchee un browser real — el UA identificatorio original (`colonial-museum-routes/0.1 (...)`, siguiendo la convención educada de scrapers que se identifican) se cae en el filtro de firma antes de que importen el crawl-delay o la URL pedida. `fetch_bm.py` usa un User-Agent de Chrome real + headers `Accept`/`Accept-Language` estándar para esquivar ese filtro — el comportamiento (1 objeto por request, 20s de por medio, mismas rutas permitidas por robots.txt) no cambia, solo la firma del header.

### Hallazgo estructural: el Louvre no tiene departamento de África/América

Los 9 departamentos curatoriales del Louvre son todos Egipto/Medio Oriente/Mediterráneo/Europa (Antigüedades Egipcias, Orientales, Griegas-Etruscas-Romanas, Arte Bizantino, Arte Islámico, Pinturas, Escultura, Artes Decorativas, Artes Gráficas) — **no hay Sub-Saharan Africa ni América**. Ese fondo se transfirió al Musée du Quai Branly cuando abrió en 2006. Por eso las líneas del Louvre en el mapa van a seguir concentradas en Egipto/Medio Oriente casi sin importar cuánto se amplíe el piloto — no es un sesgo de muestreo, es la colección real. Si en algún momento se quiere cubrir el ángulo Francia-África/Caribe específicamente, el museo correcto sería Quai Branly (implicaría sumar una cuarta fuente, fuera del alcance actual de 3 museos).

### Capa de contexto: imperios coloniales circa 1920 (`colonial_overlay.geojson`)

Fondo visual (no forma parte de las 3 capas del modelo de datos — no está ligado a ninguna pieza puntual) que sombrea qué regiones fueron colonia de UK o Francia, para explicar visualmente por qué las líneas del BM y el Louvre van a donde van.

**EEUU queda afuera a propósito**: el Met no adquirió sus piezas porque EEUU controlara los territorios de origen (Egipto, Medio Oriente, África, Asia) — las consiguió por mercado internacional de antigüedades, misiones de excavación autorizadas por la potencia colonial de turno, donantes ricos. El fenómeno relevante para el Met es otro (mercado del arte global beneficiándose de lo que otros extrajeron), no expansión territorial estadounidense. Decisión tomada explícitamente con el usuario — no es un descuido.

**Fuente de datos**: se evaluó primero [historical-basemaps](https://github.com/aourednik/historical-basemaps) (tiene exactamente el campo `SUBJECTO` para esto) pero está licenciado **GPLv3** — copyleft fuerte, no conviene para un repo de portfolio. Se usa en cambio **[Cliopatria](https://github.com/Seshat-Global-History-Databank/cliopatria)** (Seshat Global History Databank, Oxford), licenciado **CC-BY 4.0** (solo exige atribución, ya presente en el crédito visible del mapa y acá). Cliopatria modela a Francia como una serie de regímenes/repúblicas sucesivas (sin una entidad agregada "French Colonial Empire"), así que el snapshot de 1920 se arma sumando `French Africa` + `French Indochina` + `French Mandate for Syria and Lebanon`. UK tiene una entidad agregada, `British Colonial Empire`, pero **no cubre África continental** (ver bug encontrado y corregido el 18/08 más abajo) — hace falta sumarle `British Africa` + `British Cape Colony` + `British East Africa`, además de `British Raj` (India). Las entradas entre paréntesis del dataset (ej. `(British Empire)`) son de tipo RELATION (vasallaje/alianza), no territorio real — se descartan.

`src/fetch_colonial_overlay.py` baja y cachea el geojson completo de Cliopatria (~165MB sin comprimir — nunca se commitea, ver `.gitignore`) en `data/raw/`, y exporta los polígonos filtrados a `web/public/colonial_overlay.geojson` (sí se commitea). Tres modos: `--export --year N` (snapshot de un solo año, ya no se usa desde que existe el timeline pero se deja para debugging puntual), `--export-timeline --min-year N --max-year N` (todos los polígonos de las entidades coloniales cuyo rango se solapa con `[min-year, max-year]`, con su propio `FromYear`/`ToYear` — es el que usa la app), y `--explore` (con `--keywords` configurable) que lista todos los nombres de entidad disponibles para UK/Francia con sus rangos de año, útil si Cliopatria cambia su nomenclatura en una release futura.

La app tiene un timeline (`Timeline.tsx`) al pie del mapa que deja arrastrar el año y filtra los polígonos vía `Layer.filter` de Mapbox (`FromYear <= año <= ToYear`), en vez de mostrar un snapshot fijo — rango 1700-2020, pensado para cubrir el rango real de `accessionYear` de las piezas (1793-2022). La capa completa es opcional: arranca colapsada, se abre con el pull-tab "Contexto colonial" al pie del mapa (ver más abajo, sección de rutas de navegación, por el resto del dock). El geojson con todas las décadas pesa varios MB (bastante más que el snapshot de un solo año), así que se sirve desde `web/public/` y se pide con `fetch()` recién la primera vez que se abre el dock, en vez de bundlearlo con `?raw` — eso lo mantenía afuera del JS principal para quien nunca abre la capa.

**Hitos puntuales en el timeline (17/08)**: además de los polígonos/rutas, el timeline marca años sueltos con un círculo pequeño + tooltip on hover (`web/src/data/historicalEvents.ts`, prop `events` de `Timeline.tsx`) — eventos institucionales que ayudan a leer las otras 2 capas, no piezas ni territorios. Arrancó con 3 hitos del Met (el museo con el mecanismo menos obvio de los 3 — no hay territorio colonial de EEUU que sombrear, así que necesita más contexto textual): 1870 (fundación, primer objeto adquirido), 1876 (compra de la Colección Cesnola, antigüedades de Chipre — estableció la reputación del Met como repositorio serio), y 1906 (arranca la Expedición Egipcia propia del Met, hasta 1935 — el quiebre real entre "financiar excavaciones ajenas" y "excavar directamente bajo autorización del gobierno egipcio de la época"). Click en el marcador salta el slider a ese año. Extensible a BM/Louvre más adelante — no cerrado a los 3 del Met.

**Hueco conocido — mandatos británicos no representados**: Cliopatria no modela el Mandato Británico de Mesopotamia (Irak, 1920-1932) ni el de Palestina como entidades propias — el polígono de `Ottoman Empire` sigue cubriendo esa zona hasta 1922-1923, y recién aparece `Kingdom of Iraq` en 1932 (ya nominalmente independiente, no colonia formal). No es un error de selección nuestro: se probó explorando con keywords `mesopotamia,iraq,palestine,transjordan,mandate,ottoman` y no hay ninguna entidad intermedia que capture ese período. Irak y Palestina quedan sin sombrear en el snapshot de 1920 pese a haber estado bajo control británico — limitación aceptada de la fuente, no vale la pena forzar una fecha distinta solo para esos dos países (complicaría el diseño de "un año, un snapshot" y de todos modos `Kingdom of Iraq` no es políticamente equivalente a un mandato).

**Bug encontrado y corregido el 18/08 — colonias británicas en África ausentes del mapa**: reportado directamente por la usuaria ("las excolonias inglesas en África no están marcadas en el mapa"). El comentario original en `UK_COLONIAL_NAMES` afirmaba que 2 entidades (`British Colonial Empire` + `British Raj`) alcanzaban para cubrir casi todo el imperio británico 1706-1999 — esa afirmación nunca se verificó contra África en particular, a diferencia del lado francés, que desde el principio se armó sumando cada colonia por región. Al inspeccionar directamente la geometría del feature `British Colonial Empire` para 1920 (137 polígonos) se confirmó que no tiene **ningún** territorio en África continental: cubre Canadá, Caribe, Malvinas, Australia/NZ, Fiji, Islas Salomón, Malasia/Borneo, Hong Kong, Papúa Nueva Guinea, una franja costera del Golfo Arábigo y Mauricio — pero nada de Egipto, Sudán, Nigeria, Kenia, Costa de Oro, Sudáfrica, etc. Corriendo `--explore` con keywords de países africanos contra el geojson crudo de Cliopatria se encontraron 3 entidades separadas que nunca se habían agregado, exactamente en paralelo al patrón ya usado para Francia (`French Africa` como entidad aditiva, no parte de ningún agregado):

- `British Africa` (1885-1960, 33 polígonos) — el grueso del período colonial africano.
- `British Cape Colony` (1796-1884, 19 polígonos) — Sudáfrica antes de que `British Africa` empiece a cubrirla.
- `British East Africa` (2 features: 1961-1968 y 1969-1972, 2 polígonos) — pese al nombre, no es la etapa "East Africa" clásica (Kenia/Uganda/Tanganica ya independientes para 1961-64): la geometría corresponde a Suazilandia (independiente en 1968) y Seychelles (independiente en 1976), los últimos territorios británicos en la región tras la ola de independencias de 1960-64. Se verificó por bounding box de cada polígono antes de decidir incluirla, no se confió en el nombre solo (mismo criterio de cautela que ya se aplicó para descartar `Kingdom of Iraq` como no-colonial, ver arriba).

Fix: las 3 entidades agregadas a `UK_COLONIAL_NAMES` en `fetch_colonial_overlay.py`, geojson regenerado (`--export-timeline --min-year 1700 --max-year 2020`, pasó de 221 a 275 polígonos totales). Verificado: el snapshot de 1920 ahora tiene un feature `British Africa` con bounding box lon -16.8 a 55.4 / lat -34.8 a 33.3 (de Sierra Leona/Gambia a Somalia, de Egipto a Sudáfrica) — cobertura africana real donde antes no había ninguna. `npm run lint`/`npm run build` limpios sin regresiones.

Se corrió como los demás `fetch_*.py`: en la máquina real del usuario, no desde este sandbox (mismo motivo que Louvre/BM — red restringida acá).

## Filosofía / alcance del proyecto

Proyecto curado para portfolio personal, no un dataset exhaustivo ni un intento de competir en cobertura con proyectos tipo [heritage-vault](https://github.com/mente123/heritage-vault). Objetivo de escala: ~150-250 piezas por museo (~500-700 total), con una capa básica pareja para todas (lo que cada museo ya publica) y un subconjunto chico de piezas "bandera" (15-30 en total, 5-10 por museo como piso, no techo) con investigación profunda tipo la de las 5 piezas egipcias del Met y las 8 del Louvre (`data/enrichment/`). No se persigue bajar departamentos completos ni el 100% de ninguna colección — la app deja esto explícito con un aviso de "muestra curada" en el mapa.

La investigación profunda (layer 3) es una línea de trabajo abierta e indefinida para los 3 museos — no se cierra al llegar al mínimo de 5-10 piezas por museo, queda disponible para seguir sumando piezas bandera en cualquier sesión futura, en cualquiera de los tres.
