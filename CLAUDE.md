**Test suite del pipeline de Python (19/08)**: cobertura deliberadamente acotada, no exhaustiva — `tests/test_geocode.py` + `tests/test_museum_id.py` (22 tests), enfocados en `geocode.py` porque es la parte del pipeline con mayor historial real de bugs (ver el bug de matching por substring del 17/08, arriba). `tests/conftest.py` agrega `src/` a `sys.path` porque `src/` es una colección de scripts, no un paquete instalable — no hay `setup.py`/`pyproject.toml` ni se planea agregar uno solo para esto. Los tests de `resolve_origin_louvre()` reproducen los dos casos reales del bug del 17/08 (Dendéra/"sur" y Luristán/"Ur" — este último es el que efectivamente detecta una reintroducción del bug, ver comentario en el test; el de Dendéra pasa igual con el matcher viejo porque "Dendéra" está antes que "Ur" en la lista, así que queda como test de correctitud del caso documentado, no de regresión). No hay tests para `fetch_*.py`/`build_dataset*.py`/`build_geography*.py` (requieren red o fixtures de datos crudos grandes) ni para el frontend — queda anotado como próxima ronda si hace falta, no bloqueante.

## Arquitectura

### Modelo de datos — 3 capas, nunca mezcladas

1. **Layer 1** (`build_dataset*.py` → `data/processed/<museo>_objects.csv`): metadata tal cual la da cada museo. No se calcula ni interpreta nada acá.
2. **Layer 2** (`build_geography*.py` → `data/processed/geography_<museo>.csv`): punto de origen geográfico, inferido por nosotros vía `geocode.py`. Separado de layer 1 a propósito: es una inferencia nuestra, no un dato del museo.
3. **Layer 3** (`data/enrichment/context.csv` + `provenance_events.csv`, poblado a mano, sin script de descarga): investigación histórica del recorrido de la pieza. **No clasifica piezas como "robadas"/"no robadas"** — el objetivo es documentar el recorrido (creación → excavación/hallazgo → transferencias → adquisición del museo → hoy), no emitir un veredicto. `event_type` es un vocabulario controlado no acusatorio (`creation`, `excavation`, `transfer`, `sale`, `gift`, `bequest`, `exchange`, `acquisition`, `loan`, `restitution`, `other`). La gran mayoría de las piezas no tiene fila en layer 3 todavía — es el estado por defecto, no una excepción, y `export_web_data.py`/`make_map.py` lo tratan como opcional.

`export_web_data.py` es el único punto que junta las 3 capas (por `objectID`) y las tira a `web/src/data/objects.json`, que consume la app React. No depende de `folium` a propósito — es solo transporte de datos.

### Multi-museo: un builder por museo, mismo shape de salida

Cada museo tiene su propio `fetch_*.py` / `build_dataset_*.py` / `build_geography_*.py` porque el shape de datos de origen es distinto en cada API/sitio, pero los tres devuelven CSVs con las mismas columnas (`objectID`, `sourceMuseum`, `sourceObjectID`, `title`, etc. en layer 1; `origin_label/precision/lat/lon`, `museum_lat/lon` en layer 2). `export_web_data.py` los itera vía `MUSEUM_SOURCES` (lista de pares objects/geography csv) — agregar un museo nuevo es agregar su par de builders + una entrada en esa lista, sin tocar el resto.

`objectID` está namespaceado como `"<museo>:<id-nativo>"` (`met:96404`, `louvre:cl010277627`, `bm:Y_EA24`) porque el id crudo no es único entre museos — ver `src/museum_id.py`. Esto NUNCA se aplica a `data/raw/*.json` (el snapshot crudo se congela tal cual lo entrega cada fuente); se aplica recién al construir layer 1.

### Geocodificación (`geocode.py`)

Sin llamadas a Nominatim en bulk (prohibido por su política de uso) — es una tabla de coordenadas armada a mano, con un `resolve_origin_*()` por museo porque cada fuente da la geografía en un formato distinto:

- **Met** (`resolve_origin`): `country`/`region`/`subregion` estructurado, con fallback a texto libre de `culture` para los departamentos Asian Art y Greek/Roman Art (casi nunca completan country/region/subregion — ahí el único dato confiable es `culture`, ej. "Roman, Cypriot"; el fallback matchea por keyword, más específico primero, para que eso resuelva a Chipre y no a Italia).
- **Louvre** (`resolve_origin_louvre`): texto libre en francés, prioridad `placeOfDiscovery` > `placeOfCreation` > `provenance`, formato jerárquico "Sitio (Región->País)".
- **BM** (`resolve_origin_bm`): texto libre en inglés con prefijo de etiqueta ("Excavated/Findspot:", "Found/Acquired:", "Made in:"), prioridad `findspot` > `productionPlace`.

Cada build script imprime las etiquetas sin resolver al correr — expandir las listas de keywords (`*_SITE_COORDS`/`*_COUNTRY_KEYWORDS`) cuando se repiten es el mecanismo esperado de mejora incremental, no un bug a corregir de una.

**Label mostrado vs. texto matcheado (17/08)**: las listas `*_SITE_COORDS`/`*_COUNTRY_KEYWORDS` matchean contra el texto crudo tal cual viene de cada fuente (inglés para Met/BM, francés para Louvre) — esa palabra clave nunca se traduce, tiene que seguir encontrando el dato crudo. Lo que sí se traduce es el `origin_label` final que ve el usuario en la ficha de la pieza (`ObjectDetail.tsx`, "Hecho en {originLabel}"): las tres `resolve_origin_*()` pasan el nombre ya resuelto (sitio/país/región matcheado, no el texto crudo completo) por `es_label()`, que busca un exónimo en el diccionario `ES_NAMES` y si no lo encuentra devuelve el nombre tal cual. Antes de este cambio, BM mostraba literalmente el findspot/productionPlace scrapeado con su prefijo ("Excavated/Findspot:", "Found/Acquired:", "Made in:") y a veces notas de registro larguísimas pegadas — ilegible para el visitante; Louvre mostraba el texto libre francés crudo en vez del sitio matcheado. `ES_NAMES` no pretende ser exhaustivo — cubre países y los sitios con exónimo español establecido y conocido; sitios arqueológicos sin traducción evidente se muestran tal cual (son nombres propios, no cambian mucho entre idiomas). Ampliarlo es el mismo mecanismo incremental que las listas de coordenadas: se agrega cuando se nota un nombre feo/sin traducir, no hace falta traducir todo de una.

**`originLabel` en inglés (17/08, segunda vuelta del toggle ES/EN)**: `resolve_origin()`/`resolve_origin_louvre()` devuelven ahora también `label_en`, resuelto vía `en_label()`/`EN_NAMES` (mismo mecanismo que `es_label()`/`ES_NAMES`, mismas claves — el Met casi no necesita entradas porque sus claves crudas ya son inglés correcto; el Louvre sí, porque sus claves son francés). El **BM es un caso aparte**: sus `display` en `BM_SITE_COORDS`/`BM_COUNTRY_KEYWORDS` nunca fueron una clave de diccionario reutilizable — eran texto final ad-hoc (a veces inglés crudo, a veces ya traducido a mano al español en rondas de curación anteriores), así que meterlos en `ES_NAMES`/`EN_NAMES` hubiera requerido las mismas ~90 entradas ad-hoc que ya vivían en la tabla. Se optó por restructurar ambas listas a **4-tuplas** `(keyword, display_es, display_en, coords)` con los dos idiomas explícitos en la fuente, sin capa de diccionario intermedia — `resolve_origin_bm()` ya no llama a `es_label()` en absoluto. `build_geography*.py` escribe `origin_label_en` (además de `origin_label`) en las 3 `geography_*.csv`; `export_web_data.py` lo expone como `originLabelEn`; `ObjectDetail.tsx`/`geo.ts` eligen el campo según `lang`, con fallback a `originLabel` si falta el par en inglés (no debería pasar — `origin.get("label_en") or origin["label"]` en cada build script es la red de seguridad).

**Bug de matching por substring plano, encontrado y corregido el 17/08**: las cinco listas de keywords (`CULTURE_KEYWORDS` del Met, `LOUVRE_SITE_COORDS`/`LOUVRE_COUNTRY_KEYWORDS`, `BM_SITE_COORDS`/`BM_COUNTRY_KEYWORDS`) matcheaban con `if keyword.lower() in texto.lower()` — substring plano, sin límites de palabra. Encontrado al investigar el Zodiaque de Dendéra (`louvre:cl010028871`) para layer 3: su `placeOfDiscovery` menciona "Chapelle Est d'Osiris **sur** le toit" (francés, "sobre"), y la keyword "Ur" (ciudad mesopotámica, en `LOUVRE_SITE_COORDS`) matcheaba como substring dentro de "sur" — la pieza se geocodificaba en Irak en vez de Egipto, sin que nada lo señalara (`origin_precision` decía "site", como si fuera un match legítimo). El mismo mecanismo de bug afectaba a **12 piezas del Louvre en total**, todas con coordenadas silenciosamente equivocadas antes de este fix: 7 piezas de Luristán + 1 de Asiria (matcheaban "Ur" dentro de "Luristan"/"Assyrie"), 1 de Asur ("Ur" dentro de "Assur"), 1 de Baalbek ("Ur" dentro de "plusieurs"), 1 de Atenas/Cápua ("Mari" dentro de "Maria"), y el propio caso de Dendera. Ninguna de las 12 tenía relación real con Ur o Mari (Siria) — se verificó el texto crudo de cada una antes de asumirlo. Fix: nueva función `_keyword_matches()` con `\b` (límites de palabra) vía regex, reemplazando los 5 sitios de matching por substring plano; además se agregaron las keywords que faltaban y que el bug había estado enmascarando (Dendera/Denderah, Asur, Baalbeck, Athènes, Luristan, Assyrie) a `LOUVRE_SITE_COORDS`/`LOUVRE_COUNTRY_KEYWORDS`, con sus entradas correspondientes en `ES_NAMES`/`EN_NAMES`. Verificado sin regresiones: Met sigue en 161/168 (96%), BM en 90/90 (100%), Louvre pasó de "215/239 resueltas, 12 de ellas mal" a 215/239 resueltas correctamente (mismo conteo total, coordenadas corregidas). Este bug es un recordatorio de que el mecanismo incremental de "agregar keywords cuando se repiten" (arriba) asume que el matching en sí es correcto — vale la pena revisar el matching, no solo la cobertura de la lista, si una pieza nueva investigada a fondo aparece en un lugar que no tiene sentido con su historia documentada.

**País moderno de origen / búsqueda "al revés" por país (19/08)**: nuevo campo `origin_country`/`origin_country_en`, separado de `origin_label` — `origin_label` sigue siendo lo más específico posible (un sitio arqueológico, una región histórica, un país), pensado para la ficha de la pieza; `origin_country` es siempre un país moderno reconocible (o `null` en el puñado de casos donde el origen es demasiado difuso para asignarle uno, ver abajo), pensado para filtrar/buscar. Dos mecanismos en `geocode.py`, según qué matcheó cada `resolve_origin_*()`:

- `KEYWORD_COUNTRY` — cuando lo que matcheó ya es (o corresponde 1:1 a) un país: las claves de `COUNTRY_COORDS`/`CULTURE_KEYWORDS` (Met) y `LOUVRE_COUNTRY_KEYWORDS` (Louvre), más `BM_COUNTRY_FIELD_OVERRIDES` para el BM (sus `BM_COUNTRY_KEYWORDS` ya traen `display_es`/`display_en` reutilizables directamente como país, salvo un puñado de excepciones: "Easter Island"→Chile, "Tibet"→China, "Trinidad"→Trinidad y Tobago, "New Guinea"→Papúa Nueva Guinea). Un puñado de regiones históricas sin país en el nombre se mapean a su país moderno más asociado sin ambigüedad real para este propósito (Luristán/Perse/Elam→Irán, Assyrie/Mésopotamie/Babylonie/Sumer→Irak, Anatolie→Turquía, Levant→Siria como aproximación). `"Proche-Orient"` (Louvre) y `"Middle East"` (Met) quedan **sin país a propósito**: son regiones demasiado difusas (todo el Cercano Oriente) para asignarles un solo país sin que sea engañoso — de ahí que 3 de las 469 piezas (2 Met, 1 Louvre) no tengan `origin_country`.
- `SITE_COUNTRY_BY_POINT` — cuando lo que matcheó es un sitio puntual (`LOUVRE_SITE_COORDS`/`BM_SITE_COORDS`/`SUBREGION_COORDS`/`REGION_COORDS`, ~150 puntos): no tiene sentido mantener un país a mano por cada sitio arqueológico, así que se generó **una sola vez, offline**, con el paquete `reverse_geocode` (dataset de ~10mil ciudades, sin red — mismo espíritu que "sin llamadas a Nominatim en bulk") corrido contra los puntos lat/lon que ya vivían en este archivo, y el resultado se horneó como tabla estática en el código fuente. `reverse_geocode` **no es una dependencia del pipeline en tiempo de ejecución** (no está en `requirements.txt`) — se instaló y usó una sola vez en una sesión de Cowork para generar estos ~150 pares, después se revisaron a mano. Un error real encontrado en esa revisión: Haida Gwaii (Columbia Británica, Canadá) resolvía a Estados Unidos porque la ciudad más cercana en el dataset de la librería era Metlakatla, Alaska — corregido a mano en la tabla.

Propagación por el pipeline: `resolve_origin()`/`resolve_origin_louvre()`/`resolve_origin_bm()`/`resolve_from_culture()` devuelven `country`/`country_en` junto con `label`/`label_en`/`precision`/`lat`/`lon`; `EDITORIAL_ORIGIN_OVERRIDES` (ver más abajo) también los trae cargados a mano (`met:910742`→Irak, `louvre:cl010256592`→Ucrania). `build_geography*.py` escribe `origin_country`/`origin_country_en` en las 3 `geography_*.csv`; `export_web_data.py` los expone como `originCountry`/`originCountryEn`. Resultado: 466 de 469 piezas con país (79 países distintos), los otros 3 son los casos "Middle East"/"Proche-Orient" de arriba.

Frontend (`geo.ts`/`App.tsx`): `groupByCountry()` agrupa **todos** los objetos (no solo los `visibleObjects` filtrados por museum-toggles/research-filter, a propósito — la idea es "¿qué piezas de este país hay en cualquiera de los 3 museos?", independiente de qué esté prendido en el mapa en ese momento). La UI es un input de texto + dropdown de sugerencias (nueva fila `country-search-row` en `top-controls`, debajo del filtro de investigación) — al elegir un país, se arma un pseudo-cluster (`{lat: 0, lon: 0, label, objects}`, mismo shape que `OriginCluster`) y se reusa `ClusterPanel`/`ObjectDetail` tal cual, sin componentes nuevos ni un tercer estado de panel: `PanelState` gana un campo opcional `kind?: "country"` que viaja junto con `cluster`/`object` (incluído en el `onBack`/prev-next existentes) para que `ClusterPanel` sepa mostrar una segunda línea por fila con el sitio de origen puntual y el museo (`showOriginAndMuseum`/`museums` props nuevas, opcionales — sin ellas el componente se comporta exactamente igual que antes, para el flujo normal de click en un punto del mapa) en vez de cultura/período/fecha, que no aportan tanto cuando los resultados vienen de sitios y museos distintos.

**Segunda vuelta (19/08, mismo día): click directo sobre un país en el mapa.** La usuaria pidió explícitamente la interacción que se había imaginado desde el principio — clickear un país en el globo, no solo buscarlo por texto — con dos partes:

  - **Nombres no coinciden 1:1**: Natural Earth usa `properties.name` en inglés, a veces abreviado (`"Dem. Rep. Congo"`, `"Bosnia and Herz."`) — no es el mismo texto que nuestro `originCountry`/`originCountryEn` (traducidos a mano, formas completas). `web/src/data/countryPolygons.ts` (`NATURAL_EARTH_NAME_TO_COUNTRY_KEY`) traduce de un lado al otro, cubriendo solo los ~79 países que efectivamente tienen piezas en la muestra — un país sin entrada ahí simplemente no encuentra `CountryGroup` al clickear (ver abajo, no pasa nada). `"North Korea"`/`"South Korea"` (dos features separadas en Natural Earth) mapean ambas al mismo `"Corea"` nuestro, porque el dato de origen (`CULTURE_KEYWORDS` del Met) no distingue cuál de las dos.

  - **Orden de capas**: `country-hit` se agrega primero en el JSX (queda debajo de `origins`/`museums` en el stack) para que un click justo sobre un punto de origen o un museo siga ganando esa feature (`e.features[0]` es la de más arriba) — el país solo responde en el resto del área del mapa.

### Descubrimiento de objetos por museo — tres estrategias distintas

- **Met**: API pública con `departmentIds`, sin restricciones — `fetch_met.py --department <id>`.
- **Louvre**: la API JSON por objeto es real (`collections.louvre.fr/en/ark:/53355/cl<id>.json`), pero el sitio **bloquea `/search/export`** en `robots.txt` y la búsqueda interactiva tiene **CAPTCHA** — no hay forma automatizada de listar objetos por departamento desde el sitio mismo. Solución: Wikidata tiene `P9394` ("Louvre Museum ARK ID", ~480k registros) cruzable con `P195` (colección = departamento curatorial, como entidad Wikidata) vía SPARQL público. Se piden ordenados por `wikibase:sitelinks` descendente para priorizar piezas documentadas/conocidas ("piezas bandera"). QIDs de departamento usados: Antigüedades Egipcias `Q3044749`, Antigüedades Orientales `Q3044751`, Antigüedades Griegas/Etruscas/Romanas `Q3044747`, Arte Islámico `Q3044748`.
- **BM**: no tiene API pública, y el puente equivalente por Wikidata (`P8565`, "British Museum object ID") **no funciona bien** — casi ningún objeto tiene el departamento curatorial cargado en `P195`, y varios valores de `P8565` no traen el prefijo de letra que la URL real necesita (tiran 404 tal cual). Se raspa directo `/collection/object/<id>` (permitido por robots.txt, que solo bloquea `/search*`, `/admin/`, etc.), pero el robots.txt pide **`Crawl-delay: 20`** (20 segundos entre requests) — se respeta a rajatabla en `fetch_bm.py`, así que bajar piezas ahí es lento. Sin descubrimiento automatizado confiable, `SEED_OBJECT_IDS` en `fetch_bm.py` es una lista curada a mano, anclada en la página oficial de ["contested objects"](https://www.britishmuseum.org/about-us/british-museum-story/contested-objects-collection) del propio Museo (Benin Bronzes, Asante Gold Regalia, Maqdala, Moai, Parthenon Sculptures) — ampliarla es manual, no hay atajo.
  - **WAF por User-Agent**: `britishmuseum.org` devuelve 403 ante cualquier User-Agent que no matchee un browser real — el UA identificatorio original (`colonial-museum-routes/0.1 (...)`, siguiendo la convención educada de scrapers que se identifican) se cae en el filtro de firma antes de que importen el crawl-delay o la URL pedida. `fetch_bm.py` usa un User-Agent de Chrome real + headers `Accept`/`Accept-Language` estándar para esquivar ese filtro — el comportamiento (1 objeto por request, 20s de por medio, mismas rutas permitidas por robots.txt) no cambia, solo la firma del header.

### Hallazgo estructural: el Louvre no tiene departamento de África/América

Los 9 departamentos curatoriales del Louvre son todos Egipto/Medio Oriente/Mediterráneo/Europa (Antigüedades Egipcias, Orientales, Griegas-Etruscas-Romanas, Arte Bizantino, Arte Islámico, Pinturas, Escultura, Artes Decorativas, Artes Gráficas) — **no hay Sub-Saharan Africa ni América**. Ese fondo se transfirió al Musée du Quai Branly cuando abrió en 2006. Por eso las líneas del Louvre en el mapa van a seguir concentradas en Egipto/Medio Oriente casi sin importar cuánto se amplíe el piloto — no es un sesgo de muestreo, es la colección real. El ángulo Francia-África/Caribe/Oceanía/Asia que el Louvre no cubre lo cubre ahora Quai Branly, sumado como 4ta fuente el 31/08 (ver "Estado del proyecto" y "Cuarta fuente" más abajo).

### App web (`web/`)

Vite + React + TypeScript. Migró de `react-leaflet` a `react-map-gl`/Mapbox GL (globo 3D) — requiere `VITE_MAPBOX_TOKEN` en `web/.env` (gitignored, no versionar). Panel lateral con máquina de estados simple: `null | {view:"cluster", cluster} | {view:"object", cluster, object}` en `App.tsx`, dos componentes (`ClusterPanel.tsx` para la lista de piezas por punto de origen, `ObjectDetail.tsx` para el timeline de una pieza). El mapa queda visible/interactivo detrás del panel siempre (layout flex, no modal). Jitter determinístico (`geo.ts`, `jitteredPoint()`) para separar visualmente piezas que comparten origen exacto, sin tocar las coordenadas reales — puramente de render.

**Jitter entre clusters distintos que colisionan en el mismo punto (31/08)**: reportado por la usuaria con un ejemplo real en Argelia — varios clusters de origen con label DISTINTO ("Aït Berdjal", "Djanet", "Tindouf (ville)", "Tidikelt", "Tlemcen (ville)", cada uno con su propia fila en `groupByOrigin`) coincidían en la misma coordenada exacta porque las 5 piezas de Quai Branly detrás de esos labels comparten el mismo fallback a nivel país (`QUAI_BRANLY_COUNTRY_COORDS`, sin sitio propio en `QUAI_BRANLY_SITE_COORDS` — ver ronda del 31/08 más arriba, casos descartados a propósito por falta de confianza en el dato). El resultado en el mapa: 5 círculos apilados pixel a pixel, solo el de arriba clickeable — mismo síntoma aunque la causa no es específica de Quai Branly, aplica a cualquier museo/país donde dos orígenes con nombre distinto caigan en la misma coordenada de fallback. `groupByOrigin()` (`geo.ts`) ahora hace una segunda pasada después de armar los clusters: agrupa por coordenada exacta (ignorando label) y, si más de un cluster distinto cae en el mismo punto, los separa con `jitteredPoint()` — mismo mecanismo que ya usan las líneas dentro de un cluster, pero con un radio mucho mayor (`CLUSTER_COLLISION_JITTER_RADIUS_DEG = 0.3`, ~30km, contra los ~2km de `JITTER_RADIUS_DEG`) porque acá hay que separar círculos enteros, no solo puntas de línea. Como `cluster.lat`/`cluster.lon` son los mismos valores que ya alimentan tanto el marker de origen (`originsGeoJSON`) como el punto de arranque de sus líneas (`linesGeoJSON`, vía `jitteredPoint(cluster.lat, cluster.lon, ...)`) y el lookup de click (`clusterKey`), mutar el cluster una sola vez en `geo.ts` alcanza — no hizo falta tocar `App.tsx`. Es puramente de render, igual que el jitter de líneas: nunca se escribe de vuelta a `originLat`/`originLon` en los datos, y no inventa una precisión que no tenemos — el label sigue mostrando el sitio específico del registro del museo (ej. "Aït Berdjal"), la posición sigue siendo aproximada (nivel país), solo se visualiza separada del resto. No aplica dentro de un mismo cluster (ya vienen fusionados por label) ni cuando dos clusters coinciden en coordenada por casualidad siendo ambos precisión "site" real (caso no encontrado en los datos actuales, pero el mecanismo los separaría igual sin que eso sea incorrecto — dos sitios que de verdad están en el mismo punto exacto redondeado a 3 decimales son, en la práctica, el mismo lugar).

**Tooltip de museos con paleta invertida (31/08, pedido de la usuaria)**: `TooltipState` (`App.tsx`) suma un campo `kind: "origin" | "museum" | "country"`, seteado en `handleMouseMove` según la layer bajo el cursor. El `Popup` le agrega la clase `map-tooltip-popup--museum` solo cuando `kind === "museum"`, y esa clase invierte el fondo/texto del tooltip (fondo oscuro `#1a1a1a`, texto claro) respecto del tratamiento default de origen/país (fondo claro, texto oscuro) — se distinguen de un vistazo sin depender de leer el texto.

**Primera ronda de feedback de usuarios de prueba (01/09)**: la usuaria compartió el proyecto con amigos y trajo 4 puntos de feedback, anotados primero como tareas. Resueltos los 3 puramente de UI en una primera pasada; el cuarto (onboarding interactivo con spotlight) se implementó en una segunda pasada el mismo día, ver más abajo.

**Onboarding interactivo con spotlight (01/09, segunda pasada)**: reemplaza la apertura automática de `WelcomeModal` en la primera visita — decidido explícitamente con la usuaria entre 3 alternativas (reemplazo total, agregar sin tocar el modal, o que el tour reemplace solo la apertura automática) que el modal de texto se mantiene intacto, accesible como siempre vía el botón "?" (bienvenida + fuentes/licencias + créditos, para quien quiera leer todo con calma) — no se borra ni se recorta contenido, solo cambia qué se muestra por default en la primera visita.

- **`SpotlightTour.tsx`** (componente nuevo): un overlay de pantalla completa con un "agujero" que resalta un elemento del DOM ya renderizado por vez, más un callout con título + 1 oración + navegación (Atrás/Siguiente/Saltar). Técnica del agujero: un `div` posicionado exactamente sobre el elemento a resaltar (`getBoundingClientRect()`), con `box-shadow: 0 0 0 9999px rgba(26,26,26,0.78)` -- el propio box-shadow, al ser enorme, oscurece el resto de la pantalla, dejando transparente solo el área del div. Más simple que un SVG mask y no depende de conocer el tamaño del viewport de antemano. El overlay entero intercepta clicks (`pointer-events: auto`) para que no se pueda interactuar con la página de fondo mientras el tour está abierto -- el agujero es puramente visual (`pointer-events: none`), ningún elemento resaltado se vuelve interactivo durante el tour, evita tener que manejar el estado de "¿el usuario tocó el filtro real durante el tour?".
- **8 pasos** (`data/tourSteps.ts` para los selectores CSS -- no traducibles --, `i18n.ts` → `tourSteps` para título+texto de cada uno, mismo patrón índice-a-índice que `historicalEvents`): 2 pasos centrados sin resaltar nada (bienvenida y cierre) + 6 apuntando a controles reales ya existentes en el DOM (`.museum-toggles`, `.research-filter-row`, `.piece-counter`, `.country-click-panel`, `.year-timeline-handle`, `.welcome-trigger-btn`) -- todos elementos que se renderizan siempre, sin importar el estado de ningún toggle, así que el selector nunca falla en encontrar el target. El texto de cada paso se recortó al mismo criterio de concisión de la ronda anterior (1 oración corta, sin repetir lo que ya explican los popovers "i" de cada control -- el tour dice qué es y para qué sirve, no cómo funciona en detalle).
- **Posicionamiento del callout**: debajo del elemento resaltado por default, o arriba si no entra (ej. `.year-timeline-handle`, pegado al piso del mapa) -- calculado con una altura estimada de callout (170px, aproximación conservadora ya que el alto real varía con el texto) en vez de medir el DOM real del callout, para no depender de un segundo render. Clamp horizontal (`Math.min`/`Math.max`) para que nunca quede recortado contra un borde del viewport -- necesario para `.welcome-trigger-btn`, pegado a la esquina superior derecha. Sin flecha/conector hacia el elemento (a diferencia del pointer del tooltip de museos, ver más arriba) -- el propio agujero del spotlight ya cumple ese rol visual, una flecha adicional hubiera sido redundante.
- **Persistencia**: key de localStorage nueva y separada (`tracing-origins-tour-seen`) de la que ya usaba el modal (`tracing-origins-welcome-seen`) a propósito -- es contenido nuevo, así que alguien que ya había cerrado el modal viejo en una visita anterior igual ve el tour una vez. El botón "?" sigue abriendo el modal de texto sin cambios; el último paso del tour agrega un link chico ("Sobre este proyecto") que cierra el tour y abre ese mismo modal, para quien quiera profundizar apenas termina.
- **Fuera de alcance a propósito**: no hay forma de "avanzar" el tour clickeando el elemento resaltado en sí (el overlay bloquea toda interacción real) -- es una demo guiada, no un tutorial interactivo que requiera que el usuario ejecute la acción. Tampoco se agregó un test automatizado (el frontend sigue sin test suite, ver "Commands" arriba) -- verificado manualmente vía `tsc -b`/`oxlint`/`vite build` limpios, sin verificación visual en navegador real en esta sesión (limitación del entorno de Cowork, no del código).

- **Pill de conteo de piezas parecía clickeable sin serlo**: compartía el mismo `border-radius: 20px` (forma de pill completa) que los botones reales de la UI (`.museum-toggle-wrap`, `.research-filter-btn`), así que se leía como un filtro más. Se le bajó el radio a 4px (una "etiqueta", no un "botón") y se agregó `cursor: default` explícito -- sin tocar color/tamaño/posición, para no perder legibilidad contra el mapa.
- **Tooltip de museos con pointer**: siguiendo el mismo feedback de diferenciación que ya había pedido la usuaria el 31/08 (paleta invertida, ver arriba), pidió además que el tooltip de museos "sobresalga en línea recta con un pointer" para identificarlos más fácil en el mapa. La regla `.map-tooltip-popup .mapboxgl-popup-tip { display: none; }` (agregada el 19/08 para todos los tooltips, ver más abajo en "Toggle de idioma...") se revierte solo para `--museum`: se reactiva la punta triangular nativa de Mapbox y se recolorea a `#1a1a1a` para los 4 anchors posibles, aunque en la práctica el popup casi siempre usa `anchor="bottom"` (caja arriba del punto, punta apuntando hacia abajo, como un pin de mapa clásico). Origen/país se quedan sin punta a propósito -- son docenas de puntos hovereados con frecuencia, la puntita ahí sería ruido visual; los museos son un puñado de puntos fijos que sirven de referencia geográfica constante, así que vale la pena que el callout apunte físicamente al punto.
- **Notas "i" de museos y capas más concisas**: la usuaria aclaró (vía pregunta de desambiguación) que "tooltips muy largos y tediosos" se refería a los popovers de texto que abren los botones "i" junto a cada museo y cada capa del timeline (`museumNotes`/`layerNotes` en `i18n.ts`), no a los tooltips cortos de hover del mapa (esos ya eran "nombre + 1 dato"). Los 4 `museumNotes` y los 2 `layerNotes` (ES y EN, 12 strings en total) se recortaron a 1-2 oraciones cada uno, sacando elaboración secundaria y citas redundantes con el popover "Fuentes y licencias"/"Muestra curada" que ya las cubre (ej. "(Cliopatria, Seshat Global History Databank)" se sacó de `layerNotes.territories` porque esa atribución ya vive en `curatedNoteTerritoriesPrefix`/`License`). Toggles por museo (`museum-toggles` en `App.tsx`) filtran objetos/líneas/puntos por `sourceMuseum`, con un contador de piezas visibles que se recalcula según el filtro activo. Colores por museo (`MUSEUM_COLORS`) se reutilizan también para la capa de imperios coloniales, a propósito — mismo rojo para BM y para "territorio ex-colonia británica", mismo teal para Louvre y "territorio ex-colonia francesa", reforzando la relación museo-territorio.

**Versión mobile (01/09, pedido explícito de la usuaria: "acomodemos la version mobile")**: la app se construyó y ajustó enteramente sobre desktop — no existía ningún `@media` breakpoint hasta esta ronda. En vez de un rediseño, se identificaron los puntos donde el layout desktop se rompe directamente en una pantalla angosta (~320-428px) y se corrigieron con un solo bloque `@media (max-width: 640px)` al final de `App.css`, agrupados por causa real:

- **`.side-panel` (el panel de detalle de pieza/cluster) tenía ancho fijo** (`flex: 0 0 380px`, hermano flex de `.map-pane` dentro de `.app-layout`) — en cualquier teléfono eso desborda el viewport o exprime el mapa a un hilo. Pasa a overlay de pantalla completa en mobile (`position: fixed; inset: 0`), que además es el patrón esperado ahí (tapa el mapa en vez de convivir al lado) en vez de intentar que quepan los dos.
- **`.top-controls` (museos + investigación, arriba a la izquierda) dependía de que sobrara espacio a la derecha** para su ancho "shrink-to-fit" (`position: absolute` con solo `left`) — en un teléfono no sobra margen, y el contenido puede terminar visualmente por detrás de los botones "?"/idioma de la esquina opuesta. Se le agrega `max-width` (`calc(100vw - 100px)`, dejando lugar para esos botones) para forzar el `flex-wrap` que `.museum-toggles`/`.research-filter-row` ya tenían pero nunca se disparaba a tiempo.
- **Los popovers de ancho fijo anclados a un pill chico** (`.museum-note` 250px, `.mechanism-menu` 280px, `.year-timeline-note` 240px) — con `left:0`/`right:0` relativo a un pill que puede estar cerca de cualquier borde en una pantalla de 320-375px, quedan recortados o directamente fuera del viewport. En vez de mantener el anclaje relativo (impredecible según qué pill se tocó), pasan a una hoja fija pegada a ambos bordes del viewport en mobile (`position: fixed; left: 12px; right: 12px; bottom: 12px`) — mismo contenido, posición siempre predecible.
- **`.year-timeline-header` mete 3 grupos (leyenda / año / capas) en una sola fila sin wrap** — no entran en el ancho disponible dentro del dock (bastante menor que el viewport, por el padding lateral del timeline). Pasa a columna en mobile: año arriba (`position: static` en vez de `absolute`, centrado), leyenda y capas debajo, cada una con su propio `flex-wrap`.
- **`SpotlightTour.tsx` (el onboarding, ver más abajo) tiene su propio fix en JS, no en CSS** — `CALLOUT_WIDTH` se pasa como inline `style`, que un `@media` en `App.css` no puede pisar (el inline style siempre gana). Se agregó un `viewportWidth` en estado (actualizado en el mismo listener de `resize` que ya recalculaba la posición del callout) y `calloutWidth = Math.min(300, viewportWidth - VIEWPORT_MARGIN*2)`, usado tanto en el ancho real del callout como en el clamp horizontal que evita que se recorte contra el borde derecho.
- **`.app-layout` suma `height: 100dvh`** (después de `height: 100vh`, no en su lugar, para que los navegadores sin soporte de `dvh` se queden con el fallback) — en Safari/Chrome de iOS, `100vh` se calcula contra el viewport sin la barra de URL, dejando una franja del mapa tapada hasta hacer scroll; `dvh` sigue el alto visible real.

**Sin verificar visualmente en un navegador real desde este entorno** — mismo límite ya documentado para el onboarding con spotlight (el sandbox de Cowork no tiene forma de abrir un navegador real/emulador móvil). Esto es la mejor corrección razonada a partir de la estructura del CSS/JSX existente, verificada solo por `tsc -b`/`oxlint`/`vite build` limpios — falta la confirmación visual de la usuaria vía `npm run dev` en un teléfono real o el modo responsive de su navegador.

Se mantienen ahí solo los ajustes que siguen siendo relevantes de forma independiente del drawer: `.side-panel` overlay, el achique de `.welcome-trigger-btn`/`.lang-toggle-btn` (botones siempre visibles, no forman parte del drawer), el tooltip de hitos del timeline, y la columna del header del timeline.
- Nuevas strings `mobileFiltersToggleLabel`/`mobileFiltersToggleAria` en `i18n.ts` (ES/EN).

**Tercera vuelta (01/09, mismo día): overlap real dentro del drawer, reportado con captura.** Al abrir el drawer, `.museum-country-label` (`position:absolute; bottom:100%` sobre su propio `.museum-country-group`, técnica pensada para desktop donde `.museum-toggles` es una sola fila) se solapaba con la fila de arriba cada vez que un grupo de país caía en una línea de wrap distinta -- el `gap` entre líneas de un `flex-wrap` no reserva espacio para contenido que escapa del flujo normal hacia arriba, solo `margin-top` en el contenedor entero (que únicamente protege la primera línea). Con 3 grupos de país + "MUSEUMS:" + el contador todos compitiendo por el ancho angosto del drawer, terminaba en varias líneas de wrap, cada una tapando texto de la de arriba -- resultado descrito como "imposible de leer".

### Capa de contexto: imperios coloniales circa 1920 (`colonial_overlay.geojson`)

Fondo visual (no forma parte de las 3 capas del modelo de datos — no está ligado a ninguna pieza puntual) que sombrea qué regiones fueron colonia de UK o Francia, para explicar visualmente por qué las líneas del BM y el Louvre van a donde van.

**EEUU queda afuera a propósito**: el Met no adquirió sus piezas porque EEUU controlara los territorios de origen (Egipto, Medio Oriente, África, Asia) — las consiguió por mercado internacional de antigüedades, misiones de excavación autorizadas por la potencia colonial de turno, donantes ricos. El fenómeno relevante para el Met es otro (mercado del arte global beneficiándose de lo que otros extrajeron), no expansión territorial estadounidense. Decisión tomada explícitamente con el usuario — no es un descuido.

**Fuente de datos**: se evaluó primero [historical-basemaps](https://github.com/aourednik/historical-basemaps) (tiene exactamente el campo `SUBJECTO` para esto) pero está licenciado **GPLv3** — copyleft fuerte, no conviene para un repo de portfolio. Se usa en cambio **[Cliopatria](https://github.com/Seshat-Global-History-Databank/cliopatria)** (Seshat Global History Databank, Oxford), licenciado **CC-BY 4.0** (solo exige atribución, ya presente en el crédito visible del mapa y acá). Cliopatria modela a Francia como una serie de regímenes/repúblicas sucesivas (sin una entidad agregada "French Colonial Empire"), así que el snapshot de 1920 se arma sumando `French Africa` + `French Indochina` + `French Mandate for Syria and Lebanon`. UK tiene una entidad agregada, `British Colonial Empire`, pero **no cubre África continental** (ver bug encontrado y corregido el 18/08 más abajo) — hace falta sumarle `British Africa` + `British Cape Colony` + `British East Africa`, además de `British Raj` (India). Las entradas entre paréntesis del dataset (ej. `(British Empire)`) son de tipo RELATION (vasallaje/alianza), no territorio real — se descartan.

`src/fetch_colonial_overlay.py` baja y cachea el geojson completo de Cliopatria (~165MB sin comprimir — nunca se commitea, ver `.gitignore`) en `data/raw/`, y exporta los polígonos filtrados a `web/public/colonial_overlay.geojson` (sí se commitea). Tres modos: `--export --year N` (snapshot de un solo año, ya no se usa desde que existe el timeline pero se deja para debugging puntual), `--export-timeline --min-year N --max-year N` (todos los polígonos de las entidades coloniales cuyo rango se solapa con `[min-year, max-year]`, con su propio `FromYear`/`ToYear` — es el que usa la app), y `--explore` (con `--keywords` configurable) que lista todos los nombres de entidad disponibles para UK/Francia con sus rangos de año, útil si Cliopatria cambia su nomenclatura en una release futura.

La app tiene un timeline (`Timeline.tsx`) al pie del mapa que deja arrastrar el año y filtra los polígonos vía `Layer.filter` de Mapbox (`FromYear <= año <= ToYear`), en vez de mostrar un snapshot fijo — rango 1700-2020, pensado para cubrir el rango real de `accessionYear` de las piezas (1793-2022). La capa completa es opcional: arranca colapsada, se abre con el pull-tab "Contexto colonial" al pie del mapa (ver más abajo, sección de rutas de navegación, por el resto del dock). El geojson con todas las décadas pesa varios MB (bastante más que el snapshot de un solo año), así que se sirve desde `web/public/` y se pide con `fetch()` recién la primera vez que se abre el dock, en vez de bundlearlo con `?raw` — eso lo mantenía afuera del JS principal para quien nunca abre la capa.

**Hitos puntuales en el timeline (17/08)**: además de los polígonos/rutas, el timeline marca años sueltos con un círculo pequeño + tooltip on hover (`web/src/data/historicalEvents.ts`, prop `events` de `Timeline.tsx`) — eventos institucionales que ayudan a leer las otras 2 capas, no piezas ni territorios. Arrancó con 3 hitos del Met (el museo con el mecanismo menos obvio de los 3 — no hay territorio colonial de EEUU que sombrear, así que necesita más contexto textual): 1870 (fundación, primer objeto adquirido), 1876 (compra de la Colección Cesnola, antigüedades de Chipre — estableció la reputación del Met como repositorio serio), y 1906 (arranca la Expedición Egipcia propia del Met, hasta 1935 — el quiebre real entre "financiar excavaciones ajenas" y "excavar directamente bajo autorización del gobierno egipcio de la época"). Click en el marcador salta el slider a ese año. Extensible a BM/Louvre más adelante — no cerrado a los 3 del Met.

**Hueco conocido — mandatos británicos no representados**: Cliopatria no modela el Mandato Británico de Mesopotamia (Irak, 1920-1932) ni el de Palestina como entidades propias — el polígono de `Ottoman Empire` sigue cubriendo esa zona hasta 1922-1923, y recién aparece `Kingdom of Iraq` en 1932 (ya nominalmente independiente, no colonia formal). No es un error de selección nuestro: se probó explorando con keywords `mesopotamia,iraq,palestine,transjordan,mandate,ottoman` y no hay ninguna entidad intermedia que capture ese período. Irak y Palestina quedan sin sombrear en el snapshot de 1920 pese a haber estado bajo control británico — limitación aceptada de la fuente, no vale la pena forzar una fecha distinta solo para esos dos países (complicaría el diseño de "un año, un snapshot" y de todos modos `Kingdom of Iraq` no es políticamente equivalente a un mandato).

**Bug encontrado y corregido el 18/08 — colonias británicas en África ausentes del mapa**: reportado directamente por la usuaria ("las excolonias inglesas en África no están marcadas en el mapa"). El comentario original en `UK_COLONIAL_NAMES` afirmaba que 2 entidades (`British Colonial Empire` + `British Raj`) alcanzaban para cubrir casi todo el imperio británico 1706-1999 — esa afirmación nunca se verificó contra África en particular, a diferencia del lado francés, que desde el principio se armó sumando cada colonia por región. Al inspeccionar directamente la geometría del feature `British Colonial Empire` para 1920 (137 polígonos) se confirmó que no tiene **ningún** territorio en África continental: cubre Canadá, Caribe, Malvinas, Australia/NZ, Fiji, Islas Salomón, Malasia/Borneo, Hong Kong, Papúa Nueva Guinea, una franja costera del Golfo Arábigo y Mauricio — pero nada de Egipto, Sudán, Nigeria, Kenia, Costa de Oro, Sudáfrica, etc. Corriendo `--explore` con keywords de países africanos contra el geojson crudo de Cliopatria se encontraron 3 entidades separadas que nunca se habían agregado, exactamente en paralelo al patrón ya usado para Francia (`French Africa` como entidad aditiva, no parte de ningún agregado):

- `British Africa` (1885-1960, 33 polígonos) — el grueso del período colonial africano.
- `British Cape Colony` (1796-1884, 19 polígonos) — Sudáfrica antes de que `British Africa` empiece a cubrirla.
- `British East Africa` (2 features: 1961-1968 y 1969-1972, 2 polígonos) — pese al nombre, no es la etapa "East Africa" clásica (Kenia/Uganda/Tanganica ya independientes para 1961-64): la geometría corresponde a Suazilandia (independiente en 1968) y Seychelles (independiente en 1976), los últimos territorios británicos en la región tras la ola de independencias de 1960-64. Se verificó por bounding box de cada polígono antes de decidir incluirla, no se confió en el nombre solo (mismo criterio de cautela que ya se aplicó para descartar `Kingdom of Iraq` como no-colonial, ver arriba).

Fix: las 3 entidades agregadas a `UK_COLONIAL_NAMES` en `fetch_colonial_overlay.py`, geojson regenerado (`--export-timeline --min-year 1700 --max-year 2020`, pasó de 221 a 275 polígonos totales). Verificado: el snapshot de 1920 ahora tiene un feature `British Africa` con bounding box lon -16.8 a 55.4 / lat -34.8 a 33.3 (de Sierra Leona/Gambia a Somalia, de Egipto a Sudáfrica) — cobertura africana real donde antes no había ninguna. `npm run lint`/`npm run build` limpios sin regresiones.

Se corrió como los demás `fetch_*.py`: en la máquina real del usuario, no desde este sandbox (mismo motivo que Louvre/BM — red restringida acá).

## Filosofía / alcance del proyecto

Proyecto curado para portfolio personal, no un dataset exhaustivo ni un intento de competir en cobertura con proyectos tipo [heritage-vault](https://github.com/mente123/heritage-vault). Objetivo de escala: ~150-250 piezas por museo (~500-700 total), con una capa básica pareja para todas (lo que cada museo ya publica) y un subconjunto chico de piezas "bandera" (15-30 en total, 5-10 por museo como piso, no techo) con investigación profunda tipo la de las 5 piezas egipcias del Met y las 8 del Louvre (`data/enrichment/`). No se persigue bajar departamentos completos ni el 100% de ninguna colección — la app deja esto explícito con un aviso de "muestra curada" en el mapa.

La investigación profunda (layer 3) es una línea de trabajo abierta e indefinida para los 3 museos — no se cierra al llegar al mínimo de 5-10 piezas por museo, queda disponible para seguir sumando piezas bandera en cualquier sesión futura, en cualquiera de los tres.

Primera versión (mismo día) puso el nombre del país al costado de los toggles del grupo (`museum-country-group` en fila); la usuaria pidió moverlo arriba en vez de al lado -- `museum-country-group` pasó a `flex-direction: column` con el label arriba y una fila interna nueva (`museum-country-row`) para los toggles, mismo criterio que un label de sección encabezando su contenido en vez de flotar al costado. Sin bordes/fondo nuevos, mismo motivo de siempre (`.museum-toggle-wrap` ya tiene su propio borde).

  **Cuarta vuelta (31/08, mismo día, pedido explícito de la usuaria): coordenadas a nivel sitio para declusterizar Argelia/Bolivia.** Con 165 piezas geocodificadas a nivel país nomás, varios grupos quedaban literalmente superpuestos en el mismo punto -- notado por la usuaria con Argelia y Bolivia como ejemplos, pero el problema era general (Malasia también, ver más abajo). `QUAI_BRANLY_SITE_COORDS` nuevo en `geocode.py`: mismo mecanismo de lookup exacto que `QUAI_BRANLY_COUNTRY_COORDS` (por `Toponyme.Term`, sin necesidad de `_keyword_matches()` porque es thesaurus controlado), consultado ANTES que el país en `resolve_origin_quaibranly()`. Cubre los `Toponyme` que se repiten lo suficiente como para justificar investigar su coordenada real, no las ~150 aldeas/islas únicas del dataset: La Paz/Curva/Oruro/Murillo/Lago Titicaca (Bolivia, 16+3+2+2+1 piezas), Khankhoun (Argelia, 22 piezas -- ver nota abajo), Bangkok (Tailandia, 3), Makira-Ulawa/Isabel/Nueva Georgia (islas Salomón), Nuku Hiva (Marquesas) y la Bahía de Orokolo (Papúa Nueva Guinea, 9 piezas de Hopaiku). Resultado: 67 de 165 piezas (41%) pasan de precisión `"country"` a `"region"`/`"site"` (antes 0).

  **Dos descartes deliberados, auditando el `Toponyme` COMPLETO (no solo el primer valor) antes de sumar cada entrada** -- mismo espíritu de "no inventar precisión que no tenemos" ya aplicado en el resto del pipeline:
  - **"Aït Berdjal"** (6 piezas argelinas, mismo colector -- Thérèse Rivière -- que las 22 de Khankhoun): sus 4 nombres alternativos en `Toponyme` ("L'Arbaa Naït Irathen", "Ouadhias", "Grande Kabylie") ubican la pieza en Tizi Ouzou, la Kabilia -- una región bereber distinta y geográficamente lejana de los Aurès (Chauia) donde sí cae Khankhoun (confirmado por su propio `TermPath`, que lo ubica en "Constantine (département)", el departamento colonial que cubría la zona de la misión Rivière-Tillion). Sin ninguna fuente que resuelva la contradicción entre "Aït Berdjal" y sus alternativas, se descartó -- queda a nivel país, igual que antes.
  - **Djanet/Tindouf/Tlemcen (Argelia, comercio transahariano) y Pahang/Perak (Malasia, 34 piezas)**: los 3 objetos argelinos traen como alternativa explícita "Tombouctou" (¡Malí!) o "Mauritanie" -- demasiado lejos como para confiar en el primer término del thesaurus. Y cada una de las 34 piezas malasias trae AMBOS estados (Pahang/Perak) como Toponyme, uno como principal y el otro como alternativa, en partes parejas -- ningún registro es más confiable que el otro, así que asumir el primero (como hace `_first()` en el resto del pipeline) hubiera sido fabricar una precisión de estado que el propio museo no tiene. Las 37 piezas de estos 5 términos quedan a nivel país, sin cambios.
- **Capa de rutas de navegantes (1700-1900)**: idea del usuario (16/08) — mostrar las rutas reales navegadas por potencias coloniales como capa de contexto adicional, con la misma lógica que la capa de territorios coloniales (opcional, toggle propio). Dataset candidato: **CLIWOC** (Climatological Database for the World's Oceans), ~287k entradas de bitácoras de barcos holandeses/ingleses/franceses/españoles, mayormente 1750-1850 — proyecto financiado por la UE (2001-2003), digitalizado originalmente por el KNMI. Igual que la capa colonial, deja a EEUU/Met afuera a propósito. **Licencia confirmada (16/08): CC-BY 3.0** — verificada en el registro formal de PANGAEA (Jones et al. 2007, "Climatological observations from ship logbooks between 1750 and 1854 (release 2.1)", `doi:10.1594/PANGAEA.611088`, `meta-DCTERMS.license: creativecommons.org/licenses/by/3.0`), no en el mirror informal de historicalclimatology.com/LOC que se había encontrado primero. Mismo nivel de exigencia de atribución que Cliopatria.
  - **Granularidad real del dato en PANGAEA**: no es un CSV único de 287k puntos — son 5468 datasets, uno por crucero/viaje (ej. `PANGAEA.747143` = viaje del Acasta, Cork→Carlisle Bay, feb-abr 1807), cada uno con su propio bloque de metadata `Event` (nombre de barco, tipo, `Company` — ej. "Royal Navy", útil como proxy de nacionalidad —, 1er observador/capitán, fecha y lat/lon de inicio y fin de crucero) y un archivo tab-delimited con la serie completa de observaciones diarias (fecha/lat/lon/viento/presión/temperatura por entrada). Esto es en realidad mejor para una capa de "rutas" que el crudo de 287k puntos sueltos: cada dataset ya es una ruta con inicio/fin definidos.
  - **Implementado y cableado en el mapa (16/08): `src/fetch_navigator_routes.py`**, mismo patrón que `fetch_colonial_overlay.py` — baja y cachea el ZIP completo (`?format=zip` sobre `PANGAEA.611088`, 5468 archivos, extensión real `.tab` no `.txt`) en `data/raw/cliwoc_pangaea/` (gitignoreado, nunca se commitea), parsea el bloque de metadata `/* ... */` de cada archivo con regex, y exporta un GeoJSON a `web/public/navigator_routes.geojson`.
  - **La nación NO se identifica por el campo `Company` del Event** (enfoque original, descartado tras probarlo contra datos reales) — `Company` (ej. "Royal Navy", "VOC", "EIC") solo está poblado para barcos británicos y neerlandeses; las bitácoras francesas y españolas de este dataset no tienen ese campo en absoluto (vienen de archivos de la Marina Real directamente, sin estructura corporativa tipo compañía comercial). La señal confiable para las 4 naciones está en la línea `Citation:`, que siempre termina con la institución de archivo + país antes de `, PANGAEA,` (ej. `"Archivo Museo Naval Madrid, Spain"`, `"Centre d'Accueil et de Recherche des Archives Nationales, Paris, France"`, `"National Maritime Museum, Greenwich, United Kingdom"`) — se clasifica por ahí (`classify_citation_country`). `Company` se conserva como dato informativo secundario en el geojson exportado (aparece en el popup cuando existe), no como clasificador.
  - **No todas las bitácoras tienen geometría**: algunas (sobre todo patrullas costeras francesas de la serie de archivo "COTE_4_JJ") solo registraron clima, no posición — quedan afuera de la capa sin importar la nación. Confirmado con `--explore-countries` contra el dataset completo: 1903/1976 UK con geometría, 161/271 Francia — de sobra para el cupo de 25+25. También se descartan cruceros cuyo inicio y fin caen en el mismo punto (patrullas que vuelven al mismo puerto — no se ven como línea en el mapa aunque la bitácora esté completa).
  - **Se buscaron los "viajes famosos" y no están**: Cook (Endeavour/Resolution/Discovery), Bougainville (Boudeuse) y La Pérouse (Boussole/Astrolabe) no aparecen en ningún dataset de la colección — CLIWOC se armó a partir de archivos de bitácoras de rutina, no de expediciones científicas de exploración. El criterio de curación es nación (UK/Francia) + bitácora más completa (`Size: N data points`, mismo espíritu que el `orderby wikibase:sitelinks` del bridge de Wikidata para el Louvre) — no fama del viaje puntual.
  - **Ruta representada como línea recta inicio→fin** (2 puntos, no la traza diaria completa). 50 rutas pesan ~12KB — nada que ver con `colonial_overlay.geojson` (4.35MB), así que no hace falta lazy-fetch adicional (se pide junto con el overlay colonial, mismo trigger `timelineOpen`, por consistencia de patrón más que por necesidad real).
  - **UI (`App.tsx`/`Timeline.tsx`)**: el dock del timeline (renombrado de "Territorios coloniales" a "Contexto colonial") ahora tiene 2 toggles independientes dentro (`showTerritories`/`showRoutes`, chips "Imperios"/"Rutas navales", arrancan ambos prendidos) — se puede ver solo imperios, solo rutas, o las dos. Las rutas comparten el mismo `Layer.filter` por `FromYear`/`ToYear` del slider que el overlay colonial (mismo nombre de campo a propósito, ver arriba) y la misma paleta de color por nación (`COLONIAL_POWER_COLORS`), pero se dibujan con `line-dasharray` para distinguirlas visualmente de las líneas sólidas pieza→museo que usan los mismos colores por museo.

**Alcance confirmado con el usuario (16/08): solo rutas UK y Francia**, no las 4 potencias que trae CLIWOC (Países Bajos y España quedan afuera). Mismo criterio que el resto de la app: cada capa de contexto corresponde a los museos que efectivamente tenemos. Agregar rutas neerlandesas/españolas solo tendría sentido si en algún momento se suma un museo de Madrid o Ámsterdam — no está planeado, pero queda la lógica anotada por si cambia el alcance del proyecto más adelante.

## Notas del entorno de desarrollo (Cowork sandbox)

Si estás operando este repo desde un sandbox con red restringida (allowlist), `requests`/`urllib` hacia `query.wikidata.org`, `collections.louvre.fr` o `britishmuseum.org` van a fallar con 403/timeout aunque el script sea correcto — los `fetch_*.py` están escritos para correr con red normal (ej. en la máquina real del usuario), no necesariamente desde ese sandbox. Para poblar datos de piloto desde un sandbox así, usar el navegador conectado (fetch dentro del contexto de la página) en vez de red directa del proceso.

Si `git commit`/`git status` desde el sandbox muestra diffs fantasma (archivos como simultáneamente borrados y untracked), el índice default de git quedó desincronizado — correr `rm -f .git/index .git/index.lock && git read-tree HEAD` antes de confiar en `git status`.
