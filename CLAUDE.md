# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Setup
pip install -r requirements.txt
cd web && npm install

# Data pipeline — corré en este orden, desde la raíz del repo
python src/fetch_met.py --department 10          # baja/mergea data/raw/met_objects_raw.json (API pública, sin key)
python src/fetch_louvre.py --per-department 60    # baja/mergea data/raw/louvre_objects_raw.json (bridge Wikidata, ver abajo)
python src/fetch_bm.py                             # baja/mergea data/raw/bm_objects_raw.json (scraper, crawl-delay 20s — lento)

python src/build_dataset.py          # layer 1 Met    -> data/processed/met_objects.csv
python src/build_dataset_louvre.py   # layer 1 Louvre -> data/processed/louvre_objects.csv
python src/build_dataset_bm.py       # layer 1 BM     -> data/processed/bm_objects.csv

python src/build_geography.py          # layer 2 Met    -> data/processed/geography.csv
python src/build_geography_louvre.py   # layer 2 Louvre -> data/processed/geography_louvre.csv
python src/build_geography_bm.py       # layer 2 BM     -> data/processed/geography_bm.csv

python src/export_web_data.py        # junta layer 1+2+3 de TODOS los museos -> web/src/data/objects.json
python src/make_map.py               # opcional: mapa estático Folium -> maps/map_pilot.html (fallback, no es la experiencia principal)

# App web (la experiencia principal)
cd web
npm run dev      # servidor local con hot reload — requiere objects.json ya generado
npm run build    # tsc -b && vite build -> web/dist
```

`export_web_data.py` no se corre solo — cada vez que cambia algo en `data/processed/` o `data/enrichment/` hay que volver a correrlo antes de ver el cambio en la app. El pipeline de Python (`src/`) no tiene test suite ni linter configurado; el frontend (`web/`) sí tiene linter (`npm run lint` → `oxlint`, configurado en `web/.oxlintrc.json`), pero tampoco tiene test suite.

## Arquitectura

### Modelo de datos — 3 capas, nunca mezcladas

1. **Layer 1** (`build_dataset*.py` → `data/processed/<museo>_objects.csv`): metadata tal cual la da cada museo. No se calcula ni interpreta nada acá.
2. **Layer 2** (`build_geography*.py` → `data/processed/geography_<museo>.csv`): punto de origen geográfico, inferido por nosotros vía `geocode.py`. Separado de layer 1 a propósito: es una inferencia nuestra, no un dato del museo.
3. **Layer 3** (`data/enrichment/context.csv` + `provenance_events.csv`, poblado a mano, sin script de descarga): investigación histórica del recorrido de la pieza. **No clasifica piezas como "robadas"/"no robadas"** — el objetivo es documentar el recorrido (creación → excavación/hallazgo → transferencias → adquisición del museo → hoy), no emitir un veredicto. `event_type` es un vocabulario controlado no acusatorio (`creation`, `excavation`, `transfer`, `sale`, `gift`, `bequest`, `exchange`, `acquisition`, `loan`, `restitution`, `other`). La gran mayoría de las piezas no tiene fila en layer 3 todavía — es el estado por defecto, no una excepción, y `export_web_data.py`/`make_map.py` lo tratan como opcional.

`export_web_data.py` es el único punto que junta las 3 capas (por `objectID`) y las tira a `web/src/data/objects.json`, que consume la app React. No depende de `folium` a propósito — es solo transporte de datos.

### Multi-museo: un builder por museo, mismo shape de salida

Cada museo tiene su propio `fetch_*.py` / `build_dataset_*.py` / `build_geography_*.py` porque el shape de datos de origen es distinto en cada API/sitio, pero los tres devuelven CSVs con las mismas columnas (`objectID`, `sourceMuseum`, `sourceObjectID`, `title`, etc. en layer 1; `origin_label/precision/lat/lon`, `museum_lat/lon` en layer 2). `export_web_data.py` los itera vía `MUSEUM_SOURCES` (lista de pares objects/geography csv) — agregar un museo nuevo es agregar su par de builders + una entrada en esa lista, sin tocar el resto.

`objectID` está namespaceado como `"<museo>:<id-nativo>"` (`met:96404`, `louvre:cl010277627`, `bm:Y_EA24`) porque el id crudo no es único entre museos — ver `src/museum_id.py`. Esto NUNCA se aplica a `data/raw/*.json` (el snapshot crudo se congela tal cual lo entrega cada fuente); se aplica recién al construir layer 1.

### Geocodificación (`geocode.py`)

Sin llamadas a Nominatim en bulk (prohibido por su política de uso) — es una tabla de coordenadas armada a mano, con un `resolve_origin_*()` por museo porque cada fuente da la geografía en un formato distinto:

- **Met** (`resolve_origin`): `country`/`region`/`subregion` estructurado, con fallback a texto libre de `culture` para los departamentos Asian Art y Greek/Roman Art (casi nunca completan country/region/subregion — ahí el único dato confiable es `culture`, ej. "Roman, Cypriot"; el fallback matchea por keyword, más específico primero, para que eso resuelva a Chipre y no a Italia).
- **Louvre** (`resolve_origin_louvre`): texto libre en francés, prioridad `placeOfDiscovery` > `placeOfCreation` > `provenance`, formato jerárquico "Sitio (Región->País)".
- **BM** (`resolve_origin_bm`): texto libre en inglés con prefijo de etiqueta ("Excavated/Findspot:", "Found/Acquired:", "Made in:"), prioridad `findspot` > `productionPlace`.

Cada build script imprime las etiquetas sin resolver al correr — expandir las listas de keywords (`*_SITE_COORDS`/`*_COUNTRY_KEYWORDS`) cuando se repiten es el mecanismo esperado de mejora incremental, no un bug a corregir de una.

**Label mostrado vs. texto matcheado (17/08)**: las listas `*_SITE_COORDS`/`*_COUNTRY_KEYWORDS` matchean contra el texto crudo tal cual viene de cada fuente (inglés para Met/BM, francés para Louvre) — esa palabra clave nunca se traduce, tiene que seguir encontrando el dato crudo. Lo que sí se traduce es el `origin_label` final que ve el usuario en la ficha de la pieza (`ObjectDetail.tsx`, "Hecho en {originLabel}"): las tres `resolve_origin_*()` pasan el nombre ya resuelto (sitio/país/región matcheado, no el texto crudo completo) por `es_label()`, que busca un exónimo en el diccionario `ES_NAMES` y si no lo encuentra devuelve el nombre tal cual. Antes de este cambio, BM mostraba literalmente el findspot/productionPlace scrapeado con su prefijo ("Excavated/Findspot:", "Found/Acquired:", "Made in:") y a veces notas de registro larguísimas pegadas — ilegible para el visitante; Louvre mostraba el texto libre francés crudo en vez del sitio matcheado. `ES_NAMES` no pretende ser exhaustivo — cubre países y los sitios con exónimo español establecido y conocido; sitios arqueológicos sin traducción evidente se muestran tal cual (son nombres propios, no cambian mucho entre idiomas). Ampliarlo es el mismo mecanismo incremental que las listas de coordenadas: se agrega cuando se nota un nombre feo/sin traducir, no hace falta traducir todo de una.

**`originLabel` en inglés (17/08, segunda vuelta del toggle ES/EN)**: `resolve_origin()`/`resolve_origin_louvre()` devuelven ahora también `label_en`, resuelto vía `en_label()`/`EN_NAMES` (mismo mecanismo que `es_label()`/`ES_NAMES`, mismas claves — el Met casi no necesita entradas porque sus claves crudas ya son inglés correcto; el Louvre sí, porque sus claves son francés). El **BM es un caso aparte**: sus `display` en `BM_SITE_COORDS`/`BM_COUNTRY_KEYWORDS` nunca fueron una clave de diccionario reutilizable — eran texto final ad-hoc (a veces inglés crudo, a veces ya traducido a mano al español en rondas de curación anteriores), así que meterlos en `ES_NAMES`/`EN_NAMES` hubiera requerido las mismas ~90 entradas ad-hoc que ya vivían en la tabla. Se optó por restructurar ambas listas a **4-tuplas** `(keyword, display_es, display_en, coords)` con los dos idiomas explícitos en la fuente, sin capa de diccionario intermedia — `resolve_origin_bm()` ya no llama a `es_label()` en absoluto. `build_geography*.py` escribe `origin_label_en` (además de `origin_label`) en las 3 `geography_*.csv`; `export_web_data.py` lo expone como `originLabelEn`; `ObjectDetail.tsx`/`geo.ts` eligen el campo según `lang`, con fallback a `originLabel` si falta el par en inglés (no debería pasar — `origin.get("label_en") or origin["label"]` en cada build script es la red de seguridad).

**Bug de matching por substring plano, encontrado y corregido el 17/08**: las cinco listas de keywords (`CULTURE_KEYWORDS` del Met, `LOUVRE_SITE_COORDS`/`LOUVRE_COUNTRY_KEYWORDS`, `BM_SITE_COORDS`/`BM_COUNTRY_KEYWORDS`) matcheaban con `if keyword.lower() in texto.lower()` — substring plano, sin límites de palabra. Encontrado al investigar el Zodiaque de Dendéra (`louvre:cl010028871`) para layer 3: su `placeOfDiscovery` menciona "Chapelle Est d'Osiris **sur** le toit" (francés, "sobre"), y la keyword "Ur" (ciudad mesopotámica, en `LOUVRE_SITE_COORDS`) matcheaba como substring dentro de "sur" — la pieza se geocodificaba en Irak en vez de Egipto, sin que nada lo señalara (`origin_precision` decía "site", como si fuera un match legítimo). El mismo mecanismo de bug afectaba a **12 piezas del Louvre en total**, todas con coordenadas silenciosamente equivocadas antes de este fix: 7 piezas de Luristán + 1 de Asiria (matcheaban "Ur" dentro de "Luristan"/"Assyrie"), 1 de Asur ("Ur" dentro de "Assur"), 1 de Baalbek ("Ur" dentro de "plusieurs"), 1 de Atenas/Cápua ("Mari" dentro de "Maria"), y el propio caso de Dendera. Ninguna de las 12 tenía relación real con Ur o Mari (Siria) — se verificó el texto crudo de cada una antes de asumirlo. Fix: nueva función `_keyword_matches()` con `\b` (límites de palabra) vía regex, reemplazando los 5 sitios de matching por substring plano; además se agregaron las keywords que faltaban y que el bug había estado enmascarando (Dendera/Denderah, Asur, Baalbeck, Athènes, Luristan, Assyrie) a `LOUVRE_SITE_COORDS`/`LOUVRE_COUNTRY_KEYWORDS`, con sus entradas correspondientes en `ES_NAMES`/`EN_NAMES`. Verificado sin regresiones: Met sigue en 161/168 (96%), BM en 90/90 (100%), Louvre pasó de "215/239 resueltas, 12 de ellas mal" a 215/239 resueltas correctamente (mismo conteo total, coordenadas corregidas). Este bug es un recordatorio de que el mecanismo incremental de "agregar keywords cuando se repiten" (arriba) asume que el matching en sí es correcto — vale la pena revisar el matching, no solo la cobertura de la lista, si una pieza nueva investigada a fondo aparece en un lugar que no tiene sentido con su historia documentada.

### Descubrimiento de objetos por museo — tres estrategias distintas

- **Met**: API pública con `departmentIds`, sin restricciones — `fetch_met.py --department <id>`.
- **Louvre**: la API JSON por objeto es real (`collections.louvre.fr/en/ark:/53355/cl<id>.json`), pero el sitio **bloquea `/search/export`** en `robots.txt` y la búsqueda interactiva tiene **CAPTCHA** — no hay forma automatizada de listar objetos por departamento desde el sitio mismo. Solución: Wikidata tiene `P9394` ("Louvre Museum ARK ID", ~480k registros) cruzable con `P195` (colección = departamento curatorial, como entidad Wikidata) vía SPARQL público. Se piden ordenados por `wikibase:sitelinks` descendente para priorizar piezas documentadas/conocidas ("piezas bandera"). QIDs de departamento usados: Antigüedades Egipcias `Q3044749`, Antigüedades Orientales `Q3044751`, Antigüedades Griegas/Etruscas/Romanas `Q3044747`, Arte Islámico `Q3044748`.
- **BM**: no tiene API pública, y el puente equivalente por Wikidata (`P8565`, "British Museum object ID") **no funciona bien** — casi ningún objeto tiene el departamento curatorial cargado en `P195`, y varios valores de `P8565` no traen el prefijo de letra que la URL real necesita (tiran 404 tal cual). Se raspa directo `/collection/object/<id>` (permitido por robots.txt, que solo bloquea `/search*`, `/admin/`, etc.), pero el robots.txt pide **`Crawl-delay: 20`** (20 segundos entre requests) — se respeta a rajatabla en `fetch_bm.py`, así que bajar piezas ahí es lento. Sin descubrimiento automatizado confiable, `SEED_OBJECT_IDS` en `fetch_bm.py` es una lista curada a mano, anclada en la página oficial de ["contested objects"](https://www.britishmuseum.org/about-us/british-museum-story/contested-objects-collection) del propio Museo (Benin Bronzes, Asante Gold Regalia, Maqdala, Moai, Parthenon Sculptures) — ampliarla es manual, no hay atajo.
  - **WAF por User-Agent**: `britishmuseum.org` devuelve 403 ante cualquier User-Agent que no matchee un browser real — el UA identificatorio original (`colonial-museum-routes/0.1 (...)`, siguiendo la convención educada de scrapers que se identifican) se cae en el filtro de firma antes de que importen el crawl-delay o la URL pedida. `fetch_bm.py` usa un User-Agent de Chrome real + headers `Accept`/`Accept-Language` estándar para esquivar ese filtro — el comportamiento (1 objeto por request, 20s de por medio, mismas rutas permitidas por robots.txt) no cambia, solo la firma del header.

### Hallazgo estructural: el Louvre no tiene departamento de África/América

Los 9 departamentos curatoriales del Louvre son todos Egipto/Medio Oriente/Mediterráneo/Europa (Antigüedades Egipcias, Orientales, Griegas-Etruscas-Romanas, Arte Bizantino, Arte Islámico, Pinturas, Escultura, Artes Decorativas, Artes Gráficas) — **no hay Sub-Saharan Africa ni América**. Ese fondo se transfirió al Musée du Quai Branly cuando abrió en 2006. Por eso las líneas del Louvre en el mapa van a seguir concentradas en Egipto/Medio Oriente casi sin importar cuánto se amplíe el piloto — no es un sesgo de muestreo, es la colección real. Si en algún momento se quiere cubrir el ángulo Francia-África/Caribe específicamente, el museo correcto sería Quai Branly (implicaría sumar una cuarta fuente, fuera del alcance actual de 3 museos).

### App web (`web/`)

Vite + React + TypeScript. Migró de `react-leaflet` a `react-map-gl`/Mapbox GL (globo 3D) — requiere `VITE_MAPBOX_TOKEN` en `web/.env` (gitignored, no versionar). Panel lateral con máquina de estados simple: `null | {view:"cluster", cluster} | {view:"object", cluster, object}` en `App.tsx`, dos componentes (`ClusterPanel.tsx` para la lista de piezas por punto de origen, `ObjectDetail.tsx` para el timeline de una pieza). El mapa queda visible/interactivo detrás del panel siempre (layout flex, no modal). Jitter determinístico (`geo.ts`, `jitteredPoint()`) para separar visualmente piezas que comparten origen exacto, sin tocar las coordenadas reales — puramente de render.

Toggles por museo (`museum-toggles` en `App.tsx`) filtran objetos/líneas/puntos por `sourceMuseum`, con un contador de piezas visibles que se recalcula según el filtro activo. Colores por museo (`MUSEUM_COLORS`) se reutilizan también para la capa de imperios coloniales, a propósito — mismo rojo para BM y para "territorio ex-colonia británica", mismo teal para Louvre y "territorio ex-colonia francesa", reforzando la relación museo-territorio.

**Toggle de idioma ES/EN (17/08)**: `web/src/i18n.ts` centraliza todo el texto de interfaz en un diccionario `STRINGS: Record<Lang, I18nStrings>` (`Lang = "es" | "en"`); cada componente (`App.tsx`, `ClusterPanel.tsx`, `ObjectDetail.tsx`, `Timeline.tsx`, `WelcomeModal.tsx`) recibe `lang` como prop y lee `STRINGS[lang]` localmente, sin contexto/provider — el árbol de componentes es chico y poco profundo, no vale la pena la indirección. Estado `lang` vive en `App.tsx`, persistido en `localStorage` (key `tracing-origins-lang`, mismo patrón que `WELCOME_SEEN_KEY`), con un botón píldora junto al "?" de bienvenida que muestra el idioma AL QUE se cambiaría al hacer click (dice "EN" estando en español), no el idioma actual. **Alcance acordado explícitamente con el usuario el 17/08, primera vuelta**: solo texto que escribimos nosotros (botones, `MUSEUM_NOTES`, `LAYER_NOTES`, `HISTORICAL_EVENTS` labels, el modal de bienvenida, el disclaimer "muestra curada", labels del panel lateral).

**Segunda vuelta (17/08, mismo día): layer 3 y `originLabel`.** Ampliado a pedido explícito del usuario. `data/enrichment/context.csv` tiene ahora `notes_en` (además de `notes`) y `data/enrichment/provenance_events.csv` tiene `description_es`/`description_en` por evento (además del `description` original, que queda sin tocar por compatibilidad) — las 21 piezas bandera (Met 5, Louvre 8, BM 8) tienen los dos idiomas completos; el Met se escribió originalmente en inglés y se tradujo a español, Louvre/BM al revés. `export_web_data.py` expone `notesEn`/`descriptionEs`/`descriptionEn`; `ObjectDetail.tsx` elige el campo según `lang`, con fallback al campo base si falta la traducción (no debería faltar en ninguna de las 21, pero deja la app segura si se agrega una pieza bandera nueva sin traducir todavía). `originLabel` también se amplió (`label_en` en `resolve_origin()`/`resolve_origin_louvre()`/`resolve_origin_bm()`, ver detalle en la sección de geocodificación más abajo).

**Fuera de alcance a propósito, todavía**: la metadata cruda de cada pieza (`title`/`culture`/`medium`/`creditLine`) sigue tal cual la da cada museo — ya en inglés para Met/BM (no necesita traducción), pero en francés para el Louvre (~239 piezas). Se evaluó traducirla en la misma sesión del 17/08 y se decidió que **no** entra en esta vuelta: a diferencia del origin_label (que resuelve contra un puñado de ~90 sitios/países ya catalogados) o layer 3 (21 piezas, texto de investigación propia), `title`/`medium`/`creditLine` del Louvre son casi enteramente texto único por pieza (198/213/178 valores distintos sobre 239 objetos — no hay diccionario chico posible) y `medium`/`creditLine` en particular usan vocabulario técnico de catalogación de museo (materiales, técnicas de orfebrería/escultura, fórmulas de adquisición) donde una traducción automática apurada corre riesgo real de quedar mal o directamente incorrecta. Queda anotado como su propia ronda futura, no bloqueante.

### Capa de contexto: imperios coloniales circa 1920 (`colonial_overlay.geojson`)

Fondo visual (no forma parte de las 3 capas del modelo de datos — no está ligado a ninguna pieza puntual) que sombrea qué regiones fueron colonia de UK o Francia, para explicar visualmente por qué las líneas del BM y el Louvre van a donde van.

**EEUU queda afuera a propósito**: el Met no adquirió sus piezas porque EEUU controlara los territorios de origen (Egipto, Medio Oriente, África, Asia) — las consiguió por mercado internacional de antigüedades, misiones de excavación autorizadas por la potencia colonial de turno, donantes ricos. El fenómeno relevante para el Met es otro (mercado del arte global beneficiándose de lo que otros extrajeron), no expansión territorial estadounidense. Decisión tomada explícitamente con el usuario — no es un descuido.

**Fuente de datos**: se evaluó primero [historical-basemaps](https://github.com/aourednik/historical-basemaps) (tiene exactamente el campo `SUBJECTO` para esto) pero está licenciado **GPLv3** — copyleft fuerte, no conviene para un repo de portfolio. Se usa en cambio **[Cliopatria](https://github.com/Seshat-Global-History-Databank/cliopatria)** (Seshat Global History Databank, Oxford), licenciado **CC-BY 4.0** (solo exige atribución, ya presente en el crédito visible del mapa y acá). Cliopatria modela a Francia como una serie de regímenes/repúblicas sucesivas (sin una entidad agregada "French Colonial Empire"), así que el snapshot de 1920 se arma sumando `French Africa` + `French Indochina` + `French Mandate for Syria and Lebanon`. UK sí tiene una entidad agregada limpia: `British Colonial Empire` + `British Raj` (India, por si no está incluida en el agregado). Las entradas entre paréntesis del dataset (ej. `(British Empire)`) son de tipo RELATION (vasallaje/alianza), no territorio real — se descartan.

`src/fetch_colonial_overlay.py` baja y cachea el geojson completo de Cliopatria (~165MB sin comprimir — nunca se commitea, ver `.gitignore`) en `data/raw/`, y exporta los polígonos filtrados a `web/public/colonial_overlay.geojson` (sí se commitea). Tres modos: `--export --year N` (snapshot de un solo año, ya no se usa desde que existe el timeline pero se deja para debugging puntual), `--export-timeline --min-year N --max-year N` (todos los polígonos de las entidades coloniales cuyo rango se solapa con `[min-year, max-year]`, con su propio `FromYear`/`ToYear` — es el que usa la app), y `--explore` (con `--keywords` configurable) que lista todos los nombres de entidad disponibles para UK/Francia con sus rangos de año, útil si Cliopatria cambia su nomenclatura en una release futura.

La app tiene un timeline (`Timeline.tsx`) al pie del mapa que deja arrastrar el año y filtra los polígonos vía `Layer.filter` de Mapbox (`FromYear <= año <= ToYear`), en vez de mostrar un snapshot fijo — rango 1700-2020, pensado para cubrir el rango real de `accessionYear` de las piezas (1793-2022). La capa completa es opcional: arranca colapsada, se abre con el pull-tab "Contexto colonial" al pie del mapa (ver más abajo, sección de rutas de navegación, por el resto del dock). El geojson con todas las décadas pesa varios MB (bastante más que el snapshot de un solo año), así que se sirve desde `web/public/` y se pide con `fetch()` recién la primera vez que se abre el dock, en vez de bundlearlo con `?raw` — eso lo mantenía afuera del JS principal para quien nunca abre la capa.

**Hitos puntuales en el timeline (17/08)**: además de los polígonos/rutas, el timeline marca años sueltos con un círculo pequeño + tooltip on hover (`web/src/data/historicalEvents.ts`, prop `events` de `Timeline.tsx`) — eventos institucionales que ayudan a leer las otras 2 capas, no piezas ni territorios. Arrancó con 3 hitos del Met (el museo con el mecanismo menos obvio de los 3 — no hay territorio colonial de EEUU que sombrear, así que necesita más contexto textual): 1870 (fundación, primer objeto adquirido), 1876 (compra de la Colección Cesnola, antigüedades de Chipre — estableció la reputación del Met como repositorio serio), y 1906 (arranca la Expedición Egipcia propia del Met, hasta 1935 — el quiebre real entre "financiar excavaciones ajenas" y "excavar directamente bajo autorización del gobierno egipcio de la época"). Click en el marcador salta el slider a ese año. Extensible a BM/Louvre más adelante — no cerrado a los 3 del Met.

**Hueco conocido — mandatos británicos no representados**: Cliopatria no modela el Mandato Británico de Mesopotamia (Irak, 1920-1932) ni el de Palestina como entidades propias — el polígono de `Ottoman Empire` sigue cubriendo esa zona hasta 1922-1923, y recién aparece `Kingdom of Iraq` en 1932 (ya nominalmente independiente, no colonia formal). No es un error de selección nuestro: se probó explorando con keywords `mesopotamia,iraq,palestine,transjordan,mandate,ottoman` y no hay ninguna entidad intermedia que capture ese período. Irak y Palestina quedan sin sombrear en el snapshot de 1920 pese a haber estado bajo control británico — limitación aceptada de la fuente, no vale la pena forzar una fecha distinta solo para esos dos países (complicaría el diseño de "un año, un snapshot" y de todos modos `Kingdom of Iraq` no es políticamente equivalente a un mandato).

Se corrió como los demás `fetch_*.py`: en la máquina real del usuario, no desde este sandbox (mismo motivo que Louvre/BM — red restringida acá).

## Filosofía / alcance del proyecto

Proyecto curado para portfolio personal, no un dataset exhaustivo ni un intento de competir en cobertura con proyectos tipo [heritage-vault](https://github.com/mente123/heritage-vault). Objetivo de escala: ~150-250 piezas por museo (~500-700 total), con una capa básica pareja para todas (lo que cada museo ya publica) y un subconjunto chico de piezas "bandera" (15-30 en total, 5-10 por museo como piso, no techo) con investigación profunda tipo la de las 5 piezas egipcias del Met y las 8 del Louvre (`data/enrichment/`). No se persigue bajar departamentos completos ni el 100% de ninguna colección — la app deja esto explícito con un aviso de "muestra curada" en el mapa.

La investigación profunda (layer 3) es una línea de trabajo abierta e indefinida para los 3 museos — no se cierra al llegar al mínimo de 5-10 piezas por museo, queda disponible para seguir sumando piezas bandera en cualquier sesión futura, en cualquiera de los tres.

Contenido:

- **"¿Cuál es el criterio para calificar qué tan controversiales son las piezas?"** (18/08, disparado por una pregunta real de una amiga de la usuaria al mostrarle el proyecto) — expuso una confusión real: no hay ningún criterio de controversia, layer 3 documenta recorridos citados sin emitir veredicto, pero nada en la UI aclaraba que "sin investigación todavía" no es lo mismo que "evaluada y no controversial". Se distinguió el problema en dos capas: el **patrón** origen→museo (líneas del mapa + capa de imperios coloniales) está completo para las 466 piezas y es la base del argumento visual del proyecto; el **detalle investigado y citado** (layer 3) es y va a seguir siendo parcial a propósito (18/08: 58 de 466, ~12%, y sigue subiendo) — no por falta de trabajo sino porque el proyecto es una muestra curada, no un dataset exhaustivo (igual que ningún museo real tiene procedencia investigada para el grueso de su colección). **Implementado el mismo día**: nueva oración (`curatedNoteResearch` en `i18n.ts`) en el popover "Muestra curada" aclarando explícitamente que el patrón está completo pero el detalle investigado es parcial y no es un puntaje de controversia; `welcomeAboutP2` del modal de bienvenida reescrito con la misma distinción. La investigación profunda sigue como línea abierta de fondo (ver nota al final de "Estado del proyecto") — se sigue ampliando porque más información documentada es valiosa en sí misma, no para subir el porcentaje.
- **Búsqueda "al revés" por país** (anotado 17/08, no implementado): idea del usuario — en vez de partir siempre de la pieza/punto de origen en el mapa, permitir elegir/buscar un país y ver qué piezas de ahí están exhibidas en cualquiera de los 3 museos. Obstáculo identificado: hoy no hay un campo `country` normalizado por pieza — `origin_label` a veces ya es un país (`origin_precision: "country"`), pero cuando es un sitio arqueológico (ej. "Nimrud", "Saqqara") el país queda implícito en qué tabla de coordenadas matcheó, no se guarda por separado. Implementarlo requeriría agregar `country` a las tablas de sitios en `geocode.py` (mismo mecanismo incremental que `ES_NAMES`/`EN_NAMES`) y propagarlo por el pipeline hasta `objects.json`; la UI podría reusar el patrón del `ClusterPanel` (lista con miniatura + museo + link) detrás de un buscador/selector de país, sin tocar el modelo de 3 capas ni el mapa existente.
- **Basemap y fronteras políticas — evaluado el 17/08, nota de transparencia implementada el mismo día**: se revisó si el basemap de Mapbox (`mapbox://styles/mapbox/light-v11`, el estilo "classic" que usa la app) necesita ajustes de rotulado en zonas en disputa. Hallazgos:
  - **Limitación técnica confirmada**: `light-v11` no soporta el toggle de `worldview` que Mapbox ofrece para fronteras en disputa (`map.setWorldview()`, perspectivas US/CN/IN) — ese toggle solo funciona en el estilo nuevo "Standard" (`mapbox://styles/mapbox/standard`), que además trae terreno 3D y edificios por default. Cambiar de estilo para ganar ese control sería un cambio visual grande de la app, no un ajuste chico — no se justifica solo por esto.
  - **Cisjordania/Gaza** (capturas revisadas con el usuario): Mapbox rotula "West Bank"/"Gaza Strip" como entidades separadas, ni fusionadas con Israel ni con el nombre "Palestine" — la misma convención que usan Google Maps, Apple Maps y la mayoría de los atlas neutrales. No se detectó un sesgo evidente hacia un lado de la disputa.
  - **Kurdistán**: no aparece rotulado en absoluto, ni como país ni como región, en ningún nivel de zoom revisado — no es un error de rotulado a corregir, es que Mapbox no lo modela como entidad política (no es un estado; es una nación repartida entre Irak/Turquía/Irán/Siria, y solo la Región del Kurdistán iraquí tiene estatus administrativo formal). Si en algún momento se quisiera visibilizar, sería agregando una capa propia (como la de imperios coloniales), no ajustando el basemap.
  - **Hallazgo más relevante para este proyecto en particular**: `light-v11` no distingue visualmente fronteras en disputa de fronteras administrativas comunes — la línea entre Cisjordania/Israel tiene el mismo grosor y estilo que las provincias internas de Jordania o Egipto. No toma partido, pero tampoco señala "esto está en disputa"; para un proyecto sobre control territorial y disputas coloniales, ese aplanamiento visual es una tensión temática real aunque no sea parcialidad activa.
  - **Decisión**: no se justifica un cambio de estilo (alto costo visual) por un beneficio incierto. Se implementó en cambio una nota de transparencia chica (mismo patrón que la nota del hueco de mandatos británicos en Cliopatria o la de cobertura de CLIWOC): un texto siempre visible dentro del popover "Muestra curada" (`curatedNoteBasemap` en `i18n.ts`, ES/EN, sin condicionar a ningún toggle porque aplica al basemap en general, no a una capa opcional) aclarando que los límites y nombres del mapa base son la convención por default de Mapbox, no una postura editorial del proyecto.
- **Cuarta fuente: Musée du Quai Branly**: evaluar sumarlo para cubrir el ángulo Francia↔África/Caribe que el Louvre no puede mostrar (ver "Hallazgo estructural" más arriba — no tiene departamento de África Subsahariana ni América, ese fondo se transfirió a Quai Branly en 2006). Implicaría un pipeline nuevo completo (`fetch_quaibranly.py` / `build_dataset_quaibranly.py` / `build_geography_quaibranly.py`, mismo patrón que los otros tres museos) — confirmado con el usuario el 16/08 que se quiere anotar para evaluar más adelante, no arrancado todavía.
- **Capa de rutas de navegantes (1700-1900)**: idea del usuario (16/08) — mostrar las rutas reales navegadas por potencias coloniales como capa de contexto adicional, con la misma lógica que la capa de territorios coloniales (opcional, toggle propio). Dataset candidato: **CLIWOC** (Climatological Database for the World's Oceans), ~287k entradas de bitácoras de barcos holandeses/ingleses/franceses/españoles, mayormente 1750-1850 — proyecto financiado por la UE (2001-2003), digitalizado originalmente por el KNMI. Igual que la capa colonial, deja a EEUU/Met afuera a propósito. **Licencia confirmada (16/08): CC-BY 3.0** — verificada en el registro formal de PANGAEA (Jones et al. 2007, "Climatological observations from ship logbooks between 1750 and 1854 (release 2.1)", `doi:10.1594/PANGAEA.611088`, `meta-DCTERMS.license: creativecommons.org/licenses/by/3.0`), no en el mirror informal de historicalclimatology.com/LOC que se había encontrado primero. Mismo nivel de exigencia de atribución que Cliopatria.
  - **Granularidad real del dato en PANGAEA**: no es un CSV único de 287k puntos — son 5468 datasets, uno por crucero/viaje (ej. `PANGAEA.747143` = viaje del Acasta, Cork→Carlisle Bay, feb-abr 1807), cada uno con su propio bloque de metadata `Event` (nombre de barco, tipo, `Company` — ej. "Royal Navy", útil como proxy de nacionalidad —, 1er observador/capitán, fecha y lat/lon de inicio y fin de crucero) y un archivo tab-delimited con la serie completa de observaciones diarias (fecha/lat/lon/viento/presión/temperatura por entrada). Esto es en realidad mejor para una capa de "rutas" que el crudo de 287k puntos sueltos: cada dataset ya es una ruta con inicio/fin definidos.
  - **Implementado y cableado en el mapa (16/08): `src/fetch_navigator_routes.py`**, mismo patrón que `fetch_colonial_overlay.py` — baja y cachea el ZIP completo (`?format=zip` sobre `PANGAEA.611088`, 5468 archivos, extensión real `.tab` no `.txt`) en `data/raw/cliwoc_pangaea/` (gitignoreado, nunca se commitea), parsea el bloque de metadata `/* ... */` de cada archivo con regex, y exporta un GeoJSON a `web/public/navigator_routes.geojson`.
  - **La nación NO se identifica por el campo `Company` del Event** (enfoque original, descartado tras probarlo contra datos reales) — `Company` (ej. "Royal Navy", "VOC", "EIC") solo está poblado para barcos británicos y neerlandeses; las bitácoras francesas y españolas de este dataset no tienen ese campo en absoluto (vienen de archivos de la Marina Real directamente, sin estructura corporativa tipo compañía comercial). La señal confiable para las 4 naciones está en la línea `Citation:`, que siempre termina con la institución de archivo + país antes de `, PANGAEA,` (ej. `"Archivo Museo Naval Madrid, Spain"`, `"Centre d'Accueil et de Recherche des Archives Nationales, Paris, France"`, `"National Maritime Museum, Greenwich, United Kingdom"`) — se clasifica por ahí (`classify_citation_country`). `Company` se conserva como dato informativo secundario en el geojson exportado (aparece en el popup cuando existe), no como clasificador.
  - **No todas las bitácoras tienen geometría**: algunas (sobre todo patrullas costeras francesas de la serie de archivo "COTE_4_JJ") solo registraron clima, no posición — quedan afuera de la capa sin importar la nación. Confirmado con `--explore-countries` contra el dataset completo: 1903/1976 UK con geometría, 161/271 Francia — de sobra para el cupo de 25+25. También se descartan cruceros cuyo inicio y fin caen en el mismo punto (patrullas que vuelven al mismo puerto — no se ven como línea en el mapa aunque la bitácora esté completa).
  - **Se buscaron los "viajes famosos" y no están**: Cook (Endeavour/Resolution/Discovery), Bougainville (Boudeuse) y La Pérouse (Boussole/Astrolabe) no aparecen en ningún dataset de la colección — CLIWOC se armó a partir de archivos de bitácoras de rutina, no de expediciones científicas de exploración. El criterio de curación es nación (UK/Francia) + bitácora más completa (`Size: N data points`, mismo espíritu que el `orderby wikibase:sitelinks` del bridge de Wikidata para el Louvre) — no fama del viaje puntual.
  - **Ruta representada como línea recta inicio→fin** (2 puntos, no la traza diaria completa). 50 rutas pesan ~12KB — nada que ver con `colonial_overlay.geojson` (4.35MB), así que no hace falta lazy-fetch adicional (se pide junto con el overlay colonial, mismo trigger `timelineOpen`, por consistencia de patrón más que por necesidad real).
  - **UI (`App.tsx`/`Timeline.tsx`)**: el dock del timeline (renombrado de "Territorios coloniales" a "Contexto colonial") ahora tiene 2 toggles independientes dentro (`showTerritories`/`showRoutes`, chips "Imperios"/"Rutas navales", arrancan ambos prendidos) — se puede ver solo imperios, solo rutas, o las dos. Las rutas comparten el mismo `Layer.filter` por `FromYear`/`ToYear` del slider que el overlay colonial (mismo nombre de campo a propósito, ver arriba) y la misma paleta de color por nación (`COLONIAL_POWER_COLORS`), pero se dibujan con `line-dasharray` para distinguirlas visualmente de las líneas sólidas pieza→museo que usan los mismos colores por museo.

**Alcance confirmado con el usuario (16/08): solo rutas UK y Francia**, no las 4 potencias que trae CLIWOC (Países Bajos y España quedan afuera). Mismo criterio que el resto de la app: cada capa de contexto corresponde a los museos que efectivamente tenemos. Agregar rutas neerlandesas/españolas solo tendría sentido si en algún momento se suma un museo de Madrid o Ámsterdam — no está planeado, pero queda la lógica anotada por si cambia el alcance del proyecto más adelante.

## Notas del entorno de desarrollo (Cowork sandbox)

Si estás operando este repo desde un sandbox con red restringida (allowlist), `requests`/`urllib` hacia `query.wikidata.org`, `collections.louvre.fr` o `britishmuseum.org` van a fallar con 403/timeout aunque el script sea correcto — los `fetch_*.py` están escritos para correr con red normal (ej. en la máquina real del usuario), no necesariamente desde ese sandbox. Para poblar datos de piloto desde un sandbox así, usar el navegador conectado (fetch dentro del contexto de la página) en vez de red directa del proceso.

Si `git commit`/`git status` desde el sandbox muestra diffs fantasma (archivos como simultáneamente borrados y untracked), el índice default de git quedó desincronizado — correr `rm -f .git/index .git/index.lock && git read-tree HEAD` antes de confiar en `git status`.
